# Спостерігач — запуск і налаштування (М.9, частина Б)

Замінює сесії-сторожі: `gemini_watch.ps1` раз на хвилину питає `gh` і кладе в теку вихідних рядки диспетчерові;
доставляє їх обгортка (частина А, `Send-Line`), цей скрипт сам нікому не пише. Моделі нема, токенів нема.

## Що він робить

| що | як | рядок у теці вихідних |
|---|---|---|
| коментарі #963 і PR нарядів Codex (`codex/*`, автор `mightyrochy`, гілка цього ж репозиторію) | лише автори `mightyrochy` й `chatgpt-codex-connector[bot]`; новий id — «новий», той самий id з іншим `updated_at` — «змінено» (правка не сповіщає, а тут видно за один прохід, ≤ 1 хв) | `СПОСТЕРІГАЧ КОМЕНТАР #<N> <id> <автор> <новий\|змінено>` |
| CI голів відкритих PR від `mightyrochy` | підсумок check-runs голови: усі завершені — найгірший висновок (`failure` > `timed_out` > `cancelled` > `action_required` > `success` > `neutral` > `skipped`); хоч одна не завершена чи їх нема — `pending`; рядок лише коли змінилась пара «голова + стан», `pending` у теку не йде | `СПОСТЕРІГАЧ CI #<N> <SHA40> <стан>` |
| перенос diff Codex | відповідь бота в PR `codex/<наряд>` з блоком ```` ```diff ```` → чистий worktree від голови `codex/<наряд>` → `git apply --check` → `git apply` → перевірка змінених шляхів → коміт → пуш лише в `refs/heads/codex/<наряд>` (fast-forward, без force) | `СПОСТЕРІГАЧ ПЕРЕНЕСЕНО <наряд> codex/<наряд> <SHA40> #<N>` або `СПОСТЕРІГАЧ НЕ ПЕРЕНЕСЕНО <наряд> <КОД>` |

Перший прохід лише запам'ятовує наявне (стан у `<WorkDir>\state.json`) і рядків не дає; видалений стан — нова базова лінія.
Один прохід дає не більше `-MaxRows` рядків (20), решту бере наступний прохід. Збій `gh` — код виходу 1, рядків нема,
стан не просувається: наступний прохід наздоганяє.

Коди «НЕ ПЕРЕНЕСЕНО»: `APPLY_FAILED` (не лягло чи шлях поза репозиторієм), `FFFD` (у diff U+FFFD — кирилиця зламана в дорозі,
#1558), `FORBIDDEN_PATH` (`.github/`, `аудит/адаптери/` чи `.git` у змінених файлах), `BINARY`, `SPECIAL_MODE` (символічне
посилання чи підмодуль), `TOO_BIG` (понад `-MaxDiffKB`, 128), `NO_DIFF` (блок без `diff --git`), `NO_BRANCH` (гілки
`codex/<наряд>` на GitHub нема), `EMPTY` (після застосування змін нема), `NOT_FF` (гілка вже пішла далі),
`PUSH_FAILED` (3 проходи поспіль), `COMMIT_FAILED`. Будь-який такий рядок — перенос робить сесія за `аудит/CHATGPT.md`.
Відповідь бота без блоку ```` ```diff ```` нічого, крім рядка «КОМЕНТАР», не дає. Одну відповідь переносять один раз; **та сама
відповідь, змінена боту, — знову**.

## Межа довіри

- У теку йде лише рядок, що повністю збігся з шаблоном (`-cmatch`, `\z`): числа, SHA, id, назва гілки за `SlugPattern`
  (`..`, пробіли, переноси рядка — відмова), два фіксовані автори, фіксовані слова й коди. Тексту коментаря, PR чи diff там нема.
- Коментар не від `mightyrochy` чи бота — не читається далі. Переносить лише відповідь бота; діф власника чи стороннього — ні.
- Назву гілки задає PR (`head.ref` цього ж репозиторію, автор `mightyrochy`), а не текст коментаря. Пуш — лише `refs/heads/codex/*`.
- Diff застосовується в окремому worktree без хуків (`core.hooksPath` порожній), `git apply` сам не пускає шлях поза
  worktree й `.git`; змінені файли перевіряються до коміту. Нових секретів нема: `gh` і `git` — наявні входи власника.
- **Хеші (9615):** з відповіді бота береться блок `git hash-object` (рядки `<40 hex>  <шлях>` поза блоками diff). Блоку
  нема — `НЕ ПЕРЕНЕСЕНО <наряд> NO_HASHES`. Після `git apply --recount` у worktree хешуються всі наявні змінені файли;
  множина шляхів і хеші мають збігтися повністю, інакше `HASH_MISMATCH`, гілка не рухається (обрізаний diff, що ліг
  частково, так не проходить).
- **Не робиться:** `--3way` (точна голова відома, не ліг — отже не збігся), пуш у `main` й будь-яке злиття.

## Налаштування (5 хв, під тобою, не під `gemini`)

Потрібні `gh auth status` (вхід власника) і `git push` у `mightyrochy/kod-shi-data` — як для `gemini_publish.ps1`.

```powershell
$w = "$env:USERPROFILE\gemini-watch"; New-Item -ItemType Directory -Force $w | Out-Null
$base = 'https://raw.githubusercontent.com/mightyrochy/kod-shi-data/main/аудит/адаптери/gemini'
Invoke-WebRequest "$base/gemini_watch.ps1" -OutFile "$w\gemini_watch.ps1" -UseBasicParsing
$set = @{ MultipleInstances = 'IgnoreNew'; AllowStartIfOnBatteries = $true; DontStopIfGoingOnBatteries = $true; StartWhenAvailable = $true }
$a = New-ScheduledTaskAction -Execute 'conhost.exe' -Argument "--headless powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File `"$w\gemini_watch.ps1`""
$t = New-ScheduledTaskTrigger -Once -At (Get-Date).AddMinutes(1) -RepetitionInterval (New-TimeSpan -Minutes 1)
$s = New-ScheduledTaskSettingsSet @set -ExecutionTimeLimit (New-TimeSpan -Minutes 5)
$p = New-ScheduledTaskPrincipal -UserId "$env:USERDOMAIN\$env:USERNAME" -LogonType Interactive -RunLevel Limited
Register-ScheduledTask -TaskName 'gemini-watch' -Action $a -Trigger $t -Settings $s -Principal $p
```

- `-OutDir` за замовчуванням `%USERPROFILE%\gemini-outbox` — він **має збігатися** з текою вихідних обгортки доставки
  (частина А); інша тека — додай `-OutDir` в `-Argument` і скажи диспетчерові. Тека — у профілі власника, не в `C:\Users\Public`.
- Журнал — `%USERPROFILE%\gemini-watch\watch.log` (кожен записаний рядок і причина кожної відмови); стан — `state.json` там само.
- Оновлення скрипта — той самий `Invoke-WebRequest`. Зупинити — `Disable-ScheduledTask gemini-watch`.
- Проба без запису: `powershell -File gemini_watch.ps1 -DryRun` — рядки лише в журнал, пушу нема.
