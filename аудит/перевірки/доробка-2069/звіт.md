# Доробка #2069: нові JSON-жнива й цілісність позиції

ДО — `a136a841db8fed6703c17866166514729f2875eb`. Код цієї доробки —
`9e1c6a769290f10c778f44c92b3f0447b8c156a5` поверх `157580cad`; поточний `origin/main` на початку роботи —
`790faff77`. Обидва джерела об'єднано звичайним merge в призначеній гілці
`gemini/доробка-2069`, без конфліктів.

## Що змінено

Позиція й закешовані відповіді належать одному проходу. Завершений прохід із
підтвердженим журналом запускає нові жнива зі сторінки 1, прибираючи попередній
кеш сторінок. Незавершений прохід продовжується зі своєї позиції. Кожна позиція
тепер містить SHA256 JSONL, а не лише кінцева. За розбіжності чи відсутності суми
відбудова починається з першої кешованої сторінки й дописує відсутні картки.
Явне оновлення переліку або зміна рецепта починає новий прохід.

Старий маркер кінця без SHA256 більше не доводить завершення обходу.
Проба `каталог_зависла_крамниця_json_стан.py` тепер вимагає його перевірки через
API, як і решти непідтверджених станів. Це посилення звірки. Доведений кінець
із цілим журналом відновлює втрачений підсумок обходу без запитів.

## ДО → ПІСЛЯ

Одна команда виконує ту саму пробу на точному історичному коді й робочій голові:

```text
python аудит/перевірки/доробка-2069/вимір.py
```

Вона дістає `zhnyvarka/` через `git archive a136a841...` у тимчасову теку,
використовує однакові рецепти, HTTP-відповіді й операції над JSONL. HTTP
замінено керованими відповідями; виконуються справжні магазин, розбір,
запис карток і checkpoint. Файли журналів — поза репозиторієм.

Для **кожного** сімейства Woo та Shopify:

| Випадок | ДО | ПІСЛЯ |
|---|---|---|
| Завершений прохід, додано четвертий товар | 0 HTTP, 3 картки | HTTP сторінок 1, 2; 4 картки |
| Завершений прохід, JSONL очищено | 0 карток, записано суму порожнього журналу | 3 картки, сума відбудованого журналу; 0 HTTP |
| Завершений прохід, JSONL обрізано до одного цілого рядка | 1 картка, записано суму неповного журналу | 3 картки, повна сума; 0 HTTP |
| Обрив посеред першої сторінки | Лише HTTP сторінки 2, 3 картки | Так само |
| Обрив посеред першої сторінки та очищення/обрізання JSONL | Лише HTTP сторінки 2, 3 картки | Так само |
| Збережена позиція на другій сторінці, JSONL очищено | HTTP 3, 4; 2 картки із 3, втрату підтверджено | Ті самі HTTP 3, 4; усі 3 картки |
| Збережена позиція на другій сторінці, JSONL обрізано | HTTP 3, 4; 3 картки | Так само |

ДО — 8 невдалих сценаріїв із 16, код 1; ПІСЛЯ — 16/16, код 0.
Контрольна сума збігається з фактичними байтами після кожного повтору;
кількість відновлених унікальних адрес перевіряється окремо, тому сама
сума неповного журналу не може задовольнити мірило. Повні факти — `ДО.txt`
та `ПІСЛЯ.txt`.

## Перелік місць відновлення та рішення

| Місце | Рішення |
|---|---|
| `виконавець._json_сімейство`: вибір позиції та читання сторінок | Єдиний `json_прохід.відновити` обирає нові жнива, продовження чи відбудову; перевірка до використання позиції. |
| `json_прохід.прочитати_стан` | Залишається читачем формату; рішення про довіру винесено у спільну звірку. Пошкоджений формат починає з першої сторінки. |
| `json_прохід.позначити` | Пише SHA256 при кожній позиції. Явний новий прохід прибирає всі старі JSON-сторінки до роботи з API. |
| `json_прохід.сторінка` | Атомарні сторінки з підписом рецепта збережено; їх повтор дозволяється після вибору режиму. Відбудова журналу використовує їх від початку без повторного HTTP. |
| `json_прохід.завершено`; `обхід.залишок`, `узгодити_стан`, фільтр завершених крамниць | Спільна звірка SHA256, без довіри до старого маркера без суми. Сам обхід продовжує один цикл, тому цілий доведений кінець не перезапускає жнива. |
| `виконавець._журнал`, `журнал_карток.прочитати` | Читають цілі записи й будують перелік наявних результатів; не доводять збереження всіх записів. Втрата цілих рядків виявляється SHA256 перед позицією. |
| `ЖурналПроходу.__init__`, `продовження`, `прочитати_чергу`; `виконавець._картка` | SQLite вже звіряє DONE з парою URL/ід відповіді в журналі й цілим тілом за SHA256. Відбиток рецепта або явне оновлення скидає чергу; завершена черга веде до нового пошуку. Змін не потрібно. |
| `виконавець._стан`, `_список_адреси` | Кеш адрес розділів має окремий строк 7 днів; він не є позицією JSON-проходу чи доказом DONE. Не використовується Woo/Shopify; строк повторного пошуку тут не змінювався. |
| `жниварка.main`, `перезняти_збагачення.прогін` | Пропуск готового ввімкнено лише явним `--продовжити`; новий запуск без цього прапорця не використовує готовність попереднього. Не читають JSON-позицій виконавця. |
| `перезняти_галереї._get`, його читачі в перезйомці варіантів | Явна тека кешу окремої перезйомки HTML, із супутником кінцевої адреси; не позиція обходу чи підтвердження JSONL. Не змінюється на шляху цього мірила. |
| `розвідка._сторінка` | Зберігає HTML і кадр після переходу; не відновлює позицію з них. |
| `журнал_артефакт.py`; `.github/workflows/zhnyva.yml` | Відновлюють файли перед прямим запуском виконавця. Режим визначає виправлений виконавець; workflow і латка до нього не потрібні. |

## Перевірка й межі

Команда `python аудит/перевірки/доробка-2069/перевірити.py` послідовно запускає
всі шість команд батареї `аудит/КОД.md`, усі `каталог_зависла_крамниця*.py`,
обидва виміри `каталог_проблеми_г_*` та читач `каталог_обхід_стан.py`.
Команди, повний вивід і коди — у `батарея.txt` та `проби.txt`.

Сім'я й виміри каталогу: 32/32 запусків, код 0. Чотири команди батареї
(дим, протокол, контракти, показ) — код 0. Перший запуск тесту живого шляху
та розділів гейтів зупинив технічний ліміт приладу 240 с; це не результат
їхніх перевірок. Повтор саме цих двох команд із більшим часом:

```text
python аудит/перевірки/доробка-2069/перевірити.py --довгі
```

Повний вивід повтору та його коди — `батарея_довгі.txt`.

Змін функцій із бази `pipeline.py@ac8c2ca` немає: правки в `zhnyvarka/`
не потребують запису очікуваної AST-відмінності поділу.

Власний офлайн-прогін не є незалежною перевіркою або живим обходом крамниць.

з новим товаром після завершених Woo/Shopify-жнив, очищенням і обрізанням
JSONL та продовженням після обриву — чи доходить кожна адреса до результату,
а повтор не перезапитує вже збережені сторінки?

Вад поза шляхом мірила не знайдено. Публікацію гілки й доставку звіту виконує
обгортка, PR відкриває диспетчер.
