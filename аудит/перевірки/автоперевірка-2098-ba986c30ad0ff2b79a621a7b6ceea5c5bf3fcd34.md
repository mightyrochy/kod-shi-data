# Причина HTTP 400 і підготовка фото

В архівному `ж1_вокал_просто_зручно/відповіді/seed3_29_ОПИС_V1_ОПИС_ВІДПОВІДЬ_V1.txt`
перший підпис — Photo 1, #80·23, top/sweater. Збережений склад зіставляє його з
джемпером MustHave, `ж-12335@musthave.ua`, і єдиною адресою
`https://musthave.ua/uploads/products/46736/00000045119.webp?v=1789737901`.

Повторно отримані байти: WebP 900×1350, 91 324 байти, без Content-Type.
У `відтворення400.json` цей кадр із міткою image/jpeg повернув той самий HTTP 400
«Failed to load image or audio file»; з image/webp — HTTP 400 з іншою помилкою розпізнавання.
Після перетворення — JPEG 683×1024, 64 721 байт, HTTP 200 та змістовний опис.
SHA-256 обох файлів незалежно звірено з записами. Власний запуск поточного
`підготуватиКадр` на 13 збережених фото дав 13 декодованих JPEG з довгою стороною
не більшою за 1024; MustHave побайтово збігся з `кадр-ПІСЛЯ.jpg`:

```text
Декодовано без помилок: 13 ; точний JPEG MustHave збігся
sha256 = 4a3c7c9e0966bf37cfea8e002d9947b03c9f623475f72a9454bc9e548a227762
```

Межа історичного доказу: первісні HTTP-байти ранкового виклику не збережені.
Відтворення доводить механізм на повторно отриманому кадрі з тієї самої адреси;
тотожність з ранковими байтами не встановлюється. Цю межу виконавець явно записав.

За кодом усі вкладення, що прямують до LM Studio через `живоюМоделлю`, включно з base64,
проходять `кадрБазою` → `підготуватиКадр`. Формат визначає декодер, великі фото зменшуються,
неприйнятні формати стають JPEG; непридатний вхід зберігає місце текстом і лічиться втратою.
Обходів підготовки в цьому транспорті: 0. Сирий шлях Claude зберігає допустимий малий WebP.
