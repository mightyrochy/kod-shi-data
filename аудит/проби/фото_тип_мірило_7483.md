# Evaluator7483 — CLI та gold v1

Прилад не викликає модель, мережу, build чи каталоговий runtime. Він читає120
підготовлених кадрів і заморожені результати; поточний photo_slot не активується.
Залежність — `джерела/фото_тип_контракт.py`, PR#1450, freeze
`4c7876498dc3984e8a896633a749e1905ca755c7` (runtime тотожний fc7e167c).
Таксономія та слот типу беруться зі спільного канону, не з назви чи старого опису.

Порядок один: Notebook prepare actual bytes → незалежна Astra max blind gold →
root receipt з реальними metadata/evidence commit → infer → evaluate. До actual
bytes та очей мітки pending, загального приймання немає. Тільки менеджер після
пілота дозволяє наступний обсяг; evaluator не запускає9486URL і не оцінює
популяційну точність зі стратифікованого пілота.

## CLI

```bash
python аудит/проби/фото_тип_мірило_7483.py \
  --manifest prepared-manifest.jsonl --captures capture-manifest.json \
  --gold gold.json --receipt receipt.json --results runs/INVOCATION/results.jsonl \
  --output evaluation.json
```

Опційно `--input-per-million` та `--output-per-million` задають відомі ціни для
формули на фактичному usage. Без usage/ціни вартість невідома, а не нуль.
У локального Qwen окремо є години ноутбука; нуль API-білінгу не означає нуль
ресурсної вартості. `actual_q` — унікальні attempt_id з request_performed=true
цього invocation, replay не оплачується повторно. Первісні latency/usage
replay-записів залишаються сирими свідченнями й не додаються як нові запити.
Формула для9486URL — лише умовна формула майбутнього кошторису, не виконаний прогін.

Exit0 — тільки PASS справжнього пілота. Exit1 — FAIL ланцюга/критеріїв. Exit2 —
INCOMPLETE або SYNTHETIC_ONLY. У JSON завжди є photo_acceptance; синтетика його
не вмикає навіть при ідеальних unit-числах.

## Вхідні файли

Prepared manifest та results — JSONL, по одному унікальному sample_id на рядок.
Протокол `photo-type-pilot-7483-v1`, рівно100 role=real і20 role=negative,
40 calibration=true. `blind_id=sha256(sample_id UTF8)[:16]`. Кожен запис має
sku (для service_control null), source_kind/product|service_control, source_id,
stratum, frame_target=form, crop (або target_binding.crop), image_url,
image_sha256, prepared_path, prepare_status=ready. Відносний prepared_path
читається від теки prepared manifest; actual bytes хешуються повторно.

`known_old_metadata` — лише sidecar для paired join після blind класифікації:
oldconfirmed, old_photo_slot та catalog_slot (українські core keys). Поле
catalog_type_legacy ніколи не стає кодованим фотофактом. Old-correct означає:
старе підтвердження=true і старий photo slot дорівнює канонічному слоту незалежно
названого gold item_type. Нове підтвердження у звіті — preview-рівність нового
фото-слота з catalog_slot; правильність контролюється окремим gold join.

Capture manifest/receipt перевіряє саме producer API `перевірити_кадри` та
`перевірити_привязку`. Capture version visible_item_capture.v1; records keyed
by sample_id, містять bytes_sha256=image_sha256, exact URL, crop, source_kind,
source_id і sku. Canonical capture SHA — SHA256(канонічні_байти JSON) без newline.
У report також збережений SHA фактичного capture-файла, це інший вимір.

Combined receipt:

- version=visible_item_capture_receipt.v1, protocol=photo-type-pilot-7483-v1;
- prepared_manifest_sha256 та gold_sha256 — фактичні bytes файлів, не переоформлений JSON;
- capture_manifest_sha256 — canonical SHA; dataset_revision/dataset_sha256,
  verification=actual_bytes_sha256, verified_capture_ids — усі120 stable IDs;
- reviewer — string верифікатора capture; eye_reviewer={id,session_id,model}
  справжньої незалежної Astra; blind=true; evidence_commit — справжній Git40;
- rows=[{sample_id,image_sha256}] — усі120 прив’язок.

Runner result має зафіксований API автораA: protocol/IDs/точні bindings,
model{id,revision},3 contract hashes, run_id/invocation_id/primary_invocation_id,
cache_key/attempt_id, request_performed/actual_request_count/reused,
status/observation, raw_response_text/bytes SHA/raw_response/model_text,
usage/latency_ms/UTC/error, capture{id,manifest_sha256}, gold_receipt_sha256.
Для товарного кадру contract_record перевіряється producer: raw hash,
raw→observation, enum, model/revision, schema/prompt/taxonomy hashes і capture.
Для service_control contract_record=null: його response перевіряється тією ж
схемою і capture chain, але не утворює SKU-факт чи overlay. HTTP raw декодується
повторно, message.content/response model/usage/finish_reason=stop звіряються.

## Незалежний gold v1

Gold — JSON object `{protocol,synthetic:false,annotations:[...]}`. До реальних
очей дозволений тільки pending-шаблон, не вигадані класи/рецензент. Astra бачить
review manifest/html з blind_id,image_sha256,prepared_path,width,height,mime;
ні SKU, ні URL, ні role/stratum, каталожного типу, опису, старого фото-типу або
результату інференсу. Класифікаційна мітка створюється до join з baseline.

Annotation після очей:

```json
{
  "blind_id": "opaque-16-hex",
  "image_sha256": "actual-frame-sha256",
  "frame_target": "form",
  "status": "resolved",
  "item_type": "existing-taxonomy-code",
  "reason": null,
  "reviewer": {"id":"actual-reviewer","session_id":"actual-session","model":"actual-Astra-model"},
  "blind": true,
  "actual_image_bytes_reviewed": true,
  "evidence_id": "immutable-actual-eye-evidence",
  "reviewed_at_utc": "actual-UTC"
}
```

Це структурний приклад, не gold. Status resolved має чинний item_type. Стани
ambiguous/target_not_visible мають item_type=null і явний reason. За кількох
предметів без незалежної прив’язки цілі не вгадується найбільший/центральний
об’єкт чи тип каталогу. Pending status=pending_eye_annotations не оцінюється.
Reviewer має збігатися з receipt.eye_reviewer й бути незалежним від infer run.
Мітка `negative` — лише кандидатна страта: якщо очі назвали сервісний кадр
розв’язним, evaluator не примусить unknown; cohort потребує розбору/заміни до
приймання. Runtime producer для SKU через це не послаблюється.

Synthetic negative_coded_join_control з явними synthetic_control=true та
expected_condition підтримується тільки як явно synthetic unit-дані. Він не
підміняє20 справжніх negative кадрів manager-пілота і не має SKU→URL overlay.

## Звіт і мірило

- wrong_accepted=0, false_confirmation=0; coverage=correct/resolvable≥0.95;
  old_correct_preserved/old_correct=1. Порожні два знаменники — not_evaluable,
  INCOMPLETE, ніколи100%.
- N=coded+unknown, окремі unknown/non_projected reasons, result statuses та
  gold statuses/reasons; усі ledger-рядки збережені. Недоведений receipt/binding
  не може створити coded-факт.
- paired.baseline_total_old_confirmed=8668 — історична популяція;
  pilot_old_confirmed/pilot_old_correct/pilot_new_confirmed — тільки100 товарних
  кадрів. population_after=null/not_measured. `8668→T пілота` не друкується як
  зміна всього каталогу; population_precision_estimate=null.
- activation=preview_only_no_photo_slot_overlay. Цей PR не активує чи не змінює
  чинні читачі фото/каталогу, 2.6/2.8 або фактичні дані.
