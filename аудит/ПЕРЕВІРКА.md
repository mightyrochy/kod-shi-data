# Перевірка пачки — один договір для будь-якої моделі

Одна незалежна від виконавця сесія на пачку (п.15); ставить диспетчер разом із хвилею. Читаєш наряди складників (рядки
дошки, пункти продукту, ризик), договір виконавця — лише коли питання про його дії; дошку цілою, картину, план і
передачі — ні. Тобі — пачка й правда про неї; злиття, ноутбук і архів — диспетчерові. Додаткових звірок (тіла PR,
архіву, композиції, сумісності з іншими PR) нема (власник): суму складників перед злиттям механічно звіряє диспетчер.
Межі сесії (підписки, самонагадування, субагенти) — як у виконавця (`аудит/ВИКОНАВЕЦЬ.md`, «Межі»).

## Пачка

- Гілка `<claude|codex|gemini>/pachka-<ДДММ>-<N>` від свіжого `main` + голови готових PR хвилі (файли `аудит/дошка/`
  обох боків лишаються окремими, дублі номерів перенумеровуєш у них) і один PR пачки в `main`, не чернетка: один CI
  (~25 хв) і один огляд рецензентів на всіх.
- Збираєш на 3–4 готових, решту дописуєш за листом диспетчера «додай #N <SHA>» — лише те, що йде в той самий живий
  прогін: «додай» у пачку з відкритим PR перезапускає її CI. Межа — 6–7 PR або ~150 тис. твого контексту; далі — нова
  пачка, її PR — після злиття попередньої: диспетчерові одразу «ЗАБЛОКОВАНО: чекаю злиття #N від диспетчера», «злий
  main / відкривай PR» він шле в ході злиття.
- Документні PR хвилі (оцінка живого) — теж у пачку; PR менеджера диспетчер зливає окремо.
- Перед злиттям у пачку — голова кожного PR (адаптер): виконавець міг допушити після «ГОТОВО». Чужих PR не береш (ядро,
  «Безпека»).
- `origin/main` зливаєш у гілку зі збереженням обох логік; головне дерево зайняте — `git worktree add`; неглибокий
  клон і записи поділу — `аудит/КОД.md`. Зайвих файлів у гілці нема (знімки стенда, логи, розпакований каталог,
  `--дім.json`).
- Новому рядку пачки без походження (ядро, «Дошка») дописуєш його з диффу й листа «ГОТОВО»: без мітки вади, що пройшли
  крізь перевірку, не порахувати (її мали 10 з 641 нових рядків).

## Глибина — за ризиком (п.3, п.10)

Ризик називає наряд; не назвав — визначаєш сама й пишеш у звіті. Вид задачі визначає предмет доказу, ризик —
глибину. Процесні документи: CI голови й мірило наряду (посилання, суперечності, проби ситуацій); каталог і знімок
продукту не застосовні, навіть якщо наряд назвав Р1. Нове мірило кольору — приймання за п.18 продукту, без зміни
порогу залежно від постачальника. Для коду діє таблиця:

| ризик | що міняє | глибина |
|---|---|---|
| Р0 | документи, правила, дошку | CI голови й мірило наряду |
| Р1 | код без зміни входу моделі й картки (рефакторинг, проби, прилади) | батарея, дифф проти рядків, проби сім'ї й сусідніх, один знімок 390×844 голови пачки очима — рефакторинг міняє картку непомітно для проб |
| Р2 | картку, тексти чи відбір без моделі | + ДО/ПІСЛЯ на каталозі, знімки 390×844 з `FOTO=1` очима |
| Р3 | поведінку моделі: промпт, палітру, колір, суд | + фото речей очима; живий прогін ПІСЛЯ замовляєш, але пачку ним не тримаєш (власник: сесія, що годинами чекає, не потрібна): вади живого — рядками з «внесено: #PR» |

Знахідки виконавця звіряй із його файлом дошки й листом «ГОТОВО»: пропущену в листі чи дошці — рядком
(власник 22.10). Знайдене тобою — лічбою в листі «вад знайдено: N (рядки)»: це половина виміру якості; друга — вади,
що пройшли крізь перевірку (рядки з «внесено: #PR», `аудит/КАРТИНА.md` §5).

## Очі й живий прогін (п.10, п.15, п.18)

- Батарея й проби — `аудит/КОД.md`. Дифф кожного PR — проти його рядків; гейти не замінюють очей і моделі.
- Очима (Р2+): кожна картка на знімку, тексти карток, питання й пояснення, файл вердиктів, фото речей правки; лічба ✔ —
  не перевірка. Каталог — `аудит/проби/огляд_крамниць.py <тека>`. Знахідка — рядок дошки з тим, що видно на знімку.
- Живий прогін (Р3) плануєш ти, бо знаєш пачку, — за `аудит/проби/живі_порядок.md` (що ганяти, сцени, ДО, режим,
  формат плану). План — файлом у своїй гілці, диспетчерові «ЖИВИЙ: <гілка>:<файл> | <модель> | <зусилля> | оцінка:
  сесія чи субагент».
- Один замір чи сцену оцінює субагент лише для читання (сила — `аудит/МОДЕЛІ.md`); йому — файл виводу, прогін робиш ти:
  два субагенти з'їли 60 % сесії перевірки. Прогін на багато сцен — окрема оцінка: сесію ставить диспетчер за твоїм
  рядком «оцінка:». Вердикт «ні» — лише коли вимірюваний крок справді діяв; інакше «не виміряно».

## CI й рецензії

- CI голови пачки звіряєш сама одним запитом (адаптер), коли решта перевірки готова. Ще йде — диспетчерові
  «ЗАБЛОКОВАНО: чекаю CI #PR <SHA> від диспетчера» і кінець ходу: результат він пише на пульсі. Не чекаєш і сторожа
  не просиш: очікувачі CI давали більшість пробуджень координації (26.10).
- CI червоний на ранньому кроці — сама ганяєш `cd джерела && NODE_PATH=node_modules node тест_показу.js` до кінця на
  голові.
- Автоматичні рецензії, що є на голові, розбираєш одним запитом: справжнє — правка виконавцем у його гілці, хибне — одна
  відповідь у треді. Codex оглядає PR пачки сам (чернеток — ні); «@codex review» — лише після суттєвої правки; нема його
  рецензії на зеленій голові — «Codex: нема» в листі, не чекаєш. Gemini Code Assist мовчить — не чекаєш.
- Виправлення робить виконавець тієї самої гілки (вичерпаний — нову сесію ставить диспетчер), потім знову злиття в
  пачку.

## Листи диспетчерові (спосіб — адаптер)

- «ПЕРЕВІРЕНО ПАЧКА #<PR> <повний SHA> — до злиття: #a, #b…; поза пачкою: #c (чому); ризик: Р…; вад знайдено: N
  (рядки); що змінилось (до → після, числа); знімок: <гілка>:<файл>; Codex: розібрано | нема; чекаю: <що або
  «нічого»>» — лише на зеленому CI саме цієї голови.
- «ЖИВИЙ: …», «РІШЕННЯ: <питання з варіантами>», «ПРОБЛЕМА: <що стоїть і чому>» — лише те, чого виконавець сам не
  розв'яже. Звіт і знімки — у `<claude|codex|gemini>/perevirka-<PR>`. Число звіту — лише з виводу команди цієї
  перевірки: команда й вивід — дослівно поруч; не запускала — «не виміряно», не оцінка.
