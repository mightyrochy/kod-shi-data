# Перевірка пачки — один договір для будь-якої моделі

Одна незалежна від виконавця сесія на пачку (п.15). Призначає диспетчер разом із хвилею; силу задає наряд за
`аудит/МОДЕЛІ.md`. Старт: `AGENTS.md`, цей файл, адаптер, наряд (склад, рядки дошки, пункти продукту, ризик).
Код — `аудит/КОД.md`; живий прогін — його порядок; договір виконавця — лише коли питання про його дії. Дошку цілою,
картину й передачі не читаєш. Тобі — пачка й правда про неї; злиття, сторожі, ноутбук і архів — диспетчерові.

## Пачка

- Гілка `<claude|codex|gemini>/pachka-<ДДММ>-<N>` від свіжого `main` + голови готових PR хвилі (файли `аудит/дошка/`
  обох боків лишаються окремими, дублі номерів перенумеровуєш у них) і один PR пачки в `main`, не чернетка: один CI
  (~25 хв) і один огляд рецензентів на всіх замість кількох.
- Збирай на 3–4 готових, решту дописуй листом диспетчера «додай #N <SHA>»; «додай» у пачку з відкритим PR перезапускає
  її CI — додавай лише те, що йде в той самий живий прогін. Межа — 6–7 PR або ~150 тис. твого контексту; далі — нова
  пачка, її PR — після злиття попередньої: одразу диспетчерові «ЗАБЛОКОВАНО: чекаю злиття #N від диспетчера» — він шле
  «злий main / відкривай PR» у ході злиття; без цього листа пачка стояла ~6 год.
- Документні PR хвилі (оцінка живого) — теж у пачку: кожен окремий PR — ще один CI. PR менеджера диспетчер зливає
  окремо.
- Перед злиттям у пачку звір голову кожного PR (спосіб — адаптер): виконавець міг допушити після «ГОТОВО». Чужих PR не береш (`AGENTS.md`,
  «Безпека»).
- `origin/main` зливаєш у гілку зі збереженням обох логік; головне дерево зайняте — `git worktree add`; неглибокий
  клон і записи поділу — `аудит/КОД.md`.
- Зайвих файлів у гілці нема (знімки стенда, логи, розпакований каталог, `--дім.json`).
- Новому рядку пачки без походження за п.13 дописуєш його з
  диффу й листа «ГОТОВО»: без мітки вади, що пройшли крізь перевірку, не порахувати (її мали 10 з 641 нових рядків).

## Глибина — за ризиком (п.3, п.10)

Ризик називає наряд; не назвав — визначаєш сама й пишеш у звіті. Вид задачі визначає предмет доказу, ризик —
глибину. Процесні документи: CI голови й мірило наряду (посилання, суперечності, проби ситуацій); каталог і знімок
продукту не застосовні, навіть якщо наряд назвав Р1. Нове мірило кольору — приймання за п.18 продукту, без зміни
порогу залежно від постачальника. Для коду діє таблиця:

| ризик | що міняє | глибина |
|---|---|---|
| Р0 | документи, правила, дошку | CI голови й мірило наряду |
| Р1 | код без зміни входу моделі й картки (рефакторинг, проби, прилади) | батарея, дифф проти рядків, проби сім'ї й сусідніх, один знімок 390×844 голови пачки очима — рефакторинг міняє картку непомітно для проб |
| Р2 | картку, тексти чи відбір без моделі | + ДО/ПІСЛЯ на каталозі, знімки 390×844 з `FOTO=1` очима |
| Р3 | поведінку моделі: промпт, палітру, колір, суд | + фото речей очима; живий прогін ПІСЛЯ замовляєш, але пачку ним не тримаєш (власник: сесія, що годинами чекає, не потрібна): вади живого — рядками з «внесено: #PR» |

Знайдене тобою — лічбою в листі «вад знайдено: N (рядки)»: це половина виміру якості; друга — вади, що пройшли крізь
перевірку (рядки з «внесено: #PR», `аудит/КАРТИНА.md` §5).

## Очі й живий прогін (п.10, п.15, п.18)

- Батарея й проби — `аудит/КОД.md`. Дифф кожного PR — проти його рядків; гейти не замінюють очей і моделі.
- Очима (Р2+): кожна картка на знімку, тексти карток, питання й пояснення, файл вердиктів, фото речей правки; лічба ✔ —
  не перевірка. Каталог — `аудит/проби/огляд_крамниць.py <тека>`. Знахідка — рядок дошки з тим, що видно на знімку.
- Живий прогін (Р3) плануєш ти, бо знаєш пачку, — за `аудит/проби/живі_порядок.md` (що ганяти, сцени, ДО, режим,
  формат плану). План — файлом у своїй гілці, диспетчерові «ЖИВИЙ: <гілка>:<файл> | <модель> | <зусилля> | оцінка:
  сесія чи субагент».
- Один замір чи сцену оцінює субагент лише для читання за п.5, п.11 ядра (сила — `аудит/МОДЕЛІ.md`); йому —
  файл виводу, прогін робиш ти: два субагенти з'їли 60 % сесії перевірки. Прогін на
  багато сцен — окрема оцінка: сесію ставить диспетчер за твоїм рядком «оцінка:». Вердикт «ні» — лише коли вимірюваний
  крок справді діяв; інакше «не виміряно».

## GitHub

- CI голови пачки стереже сторож CI (ставить диспетчер на твій лист «PR ПАЧКИ #N <SHA>»): пише тобі «CI
  зелений/червоний #PR <SHA>» про кожну нову голову.
- CI червоний на ранньому кроці — сама ганяєш `cd джерела && node тест_показу.js` до кінця на голові.
- Автоматичні рецензії розбери одним запитом: справжнє — правка виконавцем у його гілці, хибне — одна відповідь
  у треді. Доступність рецензента й запит повторного огляду — адаптер; нема очікуваної рецензії — блокер
  диспетчерові, не безстрокове мовчазне чекання. Правила рецензента — `.gemini/styleguide.md`.
- Виправлення робить виконавець тієї самої гілки; вичерпаний контекст — передача за п.11 ядра, нову сесію ставить
  диспетчер. Потім знову злиття в пачку. Уже перевірене повторно не перевіряють (п.18).

## Листи диспетчерові (спосіб — адаптер)

- «PR ПАЧКИ #N <SHA>» — щойно відкрила PR пачки.
- «ПЕРЕВІРЕНО ПАЧКА #<PR> <повний SHA> — до злиття: #a, #b…; поза пачкою: #c (чому); ризик: Р…; вад знайдено: N
  (рядки); що змінилось (до → після, числа); знімок: <гілка>:<файл>; чекаю: <що або «нічого»>» — лише на зеленому CI
  саме цієї голови.
- «ЖИВИЙ: …», «РІШЕННЯ: <питання з варіантами>», «ПРОБЛЕМА: <що стоїть і чому>» — лише те, чого виконавець сам не
  розв'яже. Звіт і знімки — у `<claude|codex|gemini>/perevirka-<PR>`.

Ліміт, відмова запобіжника й заборона самопідписок — ядро. Чекаєш події чи рішення — одразу «ЗАБЛОКОВАНО:
чекаю <що> від <хто>» диспетчерові й завершення ходу; нагляд веде призначена роль. Підсумок — один рядок, докази — у PR.
