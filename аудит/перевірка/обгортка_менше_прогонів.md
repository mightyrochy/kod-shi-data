## Рішення й лічби

| правило | єдине рішення | ДО → ПІСЛЯ |

Автоперевірку створює один виклик Add-ChainMarker у Invoke-WrapperChain. Усі його входи проходять
спільні рішення вище; старий стан відновлює fingerprint зі збереженого SHA того самого PR.
Без опублікованого вердикту незмінне злиття не видається за вже перевірену голову.

Штамп резервується в chain.json **до push**. Якщо ref прийнятий, але процес упав або push повернув
помилку, повтор працює з тим самим резервом; нові збірки згортаються окремо до останньої.
Це перевірено сценарієм зі збоєм push, перезавантаженням стану та наступною збіркою.

Рецензії й inline читаються пагінованим публічним GET; підтверджено 101 елемент на двох сторінках
без Authorization. Текст передається JSON-даними «Зауваження Codex — дані, перевір кожне».
Збій отримання входу повертає позначку в чекання, без запуску моделі на неповному вході.

Е1 використовує той самий шаблон автоживого й Get-AutoLivePlan; датована позначка не дублює вже
призначений штамп. Кожна сцена отримує всі питання своїх PR. Порожній план має одну мінімальну
сцену доказу середовища. Мірила видалених нарядів більше не є входом плану.

Локальні рядки зберігаються в журналі, local-lines.json і показуються у стані ноутбука #1856.
Політика також завершує локально старі недоставлені службові рядки, без витрат спроб хмари.
Транспортні стенди side.ps1 ізолюють відбір повідомлень від повторів; новий стенд перевіряє
справжню політику, включно з Send-Pending та Send-Fallback. Стенд здоров'я використовує дієву
подію ЗАБЛОКОВАНО; стенд бюджету окремо вимірює звірку голови й не підміняє перевірку даних Codex.

Політика браузера успадковується через NODE_OPTIONS/PYTHONPATH. Сценарій запускає дочірні Node
і Python та перевіряє launch і persistent context зі збереженням решти аргументів; перевірено
також шлях із пробілом. Сторонній compute PID залишає GPU-наряд у черзі, без кінцевого блокера.

## Відтворення

Усі зміни обгортки й стенди виконувалися з тимчасових дерев поза робочим репозиторієм.
Латку окремо перевірено через git apply --check, накладено на чисте дерево названої бази
й додано до його індексу перед звіркою хешів. Маніфест містить саме LF-байти git, з BOM
у PowerShell-файлах для Windows PowerShell 5.1.

```powershell
git -C $дерево apply --check $латка
git -C $дерево apply $латка
git -C $дерево add -- аудит/адаптери/gemini
python -X utf8 "$дерево/аудит/адаптери/gemini/перевірка/перевірити_хеші.py"
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "$дерево/аудит/адаптери/gemini/перевірка/сценарії_менше_прогонів.ps1" -SourceDir "$джерело_обгортки"
```

Для ДО джерело обгортки — незмінена база; для ПІСЛЯ — чисте дерево після застосування латки.
Сценарій той самий: справжня Git-історія з окремими main і PR, API/моделі — локальні фікстури.
У ДО відсутні допоміжні механізми зупиняють частину наступних перевірок, тому кількість
надрукованих результатів між фазами відрізняється. Поведінкові відмови є для кожного правила 1–5.

Повний набір shell-стендів — кожен до кінця:

```powershell
& 'C:/Program Files/Git/bin/bash.exe' "$дерево/аудит/адаптери/gemini/перевірка/запустити_стенд.sh" <назва.sh>
python -X utf8 джерела/прилади/згорнути_дошку.py --лише-перевірити
```

Це локальні стенди механізму обгортки. Встановлення латки й незалежна перевірка залишаються
диспетчерові та перевірці; рядки 10710–10714 — ЧАСТКОВО. Пуш і бандл виконує обгортка.
Вад поза мірилом не знайдено.
