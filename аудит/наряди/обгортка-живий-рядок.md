Роль — ВИКОНАВЕЦЬ (`аудит/ВИКОНАВЕЦЬ.md`), хмарна сесія; ядро — `AGENTS.md`; обгортка — `аудит/адаптери/gemini/ЧЕРГА.md`

править `аудит/адаптери/gemini/` і `.github/` прямо; PR обгортки перевіряють стенд Windows у CI і рецензія Codex.

**Чому.** 31.10 автоживий на збірці a42a1290 (злиті #2551, #2557, #2559 — усі з живим мірилом) отримав порожній план:
`Get-AutoLivePlan` (`аудит/адаптери/gemini/queue_lanes.ps1`, ~:918) бере лише рядок
`ЖИВИЙ ПІСЛЯ: <id> — <питання>`, а рядки мали вигляд «ЖИВИЙ ПІСЛЯ: серія 2 \`б1_доречність\` — …», «ЖИВИЙ ПІСЛЯ:
ж1_оціни_образ_6б (стенд: …) → …» і прозу під заголовком. Прогін пройшов мінімальною сценою, а мірила трьох PR
лишились без живого; помітив це диспетчер, читаючи звіт. Рішення менеджера 31.10 (лист диспетчерові): формат один —
`ЖИВИЙ ПІСЛЯ: <id> — <питання правки> → <режим> → <ДО звідки> → <що вважати кращим>`, id — голий, перше поле реєстру;
одна сцена — один рядок; рядок, що не розбирається чи має id поза реєстром, — CI на тілі PR до злиття (виправляє автор)
чи планувальник → ЗАБЛОКОВАНО диспетчерові.

**Інваріант ПІСЛЯ** (механізмом, одне джерело розбору, не переліком PR):
1. Розбір рядка — одне джерело для CI й планувальника: той самий вираз і той самий реєстр. Рядок тіла PR, що
   починається з `ЖИВИЙ ПІСЛЯ` (після обрізання пробілів, будь-де в тілі, зокрема під заголовком чи в списку), або
   розбирається повністю, або це вада: нема « — » після id, id з лапками чи `` ` ``, id нема першим полем у реєстрі
   свіжого дерева.
2. CI на PR до `main` (події `opened`, `synchronize`, `edited`, `ready_for_review`) читає тіло PR як дані (з
   `github.event`, через змінну середовища — без підстановки тексту в скрипт) і падає з переліком вадних рядків і
   причиною. PR без рядка `ЖИВИЙ ПІСЛЯ` — зелений. Чужий текст тіла не виконується й не потрапляє в команду оболонки.
3. Планувальник: вадний рядок у тілі злитого PR не тоне — план (JSON) несе його в окремому полі з номером PR і
   причиною; шаблон `аудит/наряди/автоживий.md` велить агентові ноутбука закінчити прогін рядком
   `ЗАБЛОКОВАНО … <PR і причина>` для диспетчера, навіть коли решта плану пройшла.
4. Сцени режиму `функція` (поле режиму реєстру) план відкладає окремо від прогонів ноутбука: ноутбук їх не жене, звіт
   автоживого називає їх «у хмарі» з PR і питанням — їх ставить диспетчер хмарною сесією (`живі_порядок.md`).
