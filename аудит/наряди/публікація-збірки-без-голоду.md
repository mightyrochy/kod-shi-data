# Публікація збірки не голодує за частих злиттів

Наряд дав диспетчер за листом менеджера 29.10 14:59 UTC (докази — субагент менеджера; перевір сам). Етап Е1 `аудит/ПЛАН.md`: автоживий бере штамп `build.txt`, тож без публікації злите наживо не перевіряють.

**Факти (лист менеджера; звір за журналами Actions `zbirka.yml` на push у main).**
- З 02:47 до 14:48 UTC 29.10 `build.txt` стояв на cd8e5ea7: щонайменше чотири публікації пропущено гілкою «main … вже новіший за джерела … і змінив paths збірки — застарілу публікацію пропущено, публікує його збірка» (`.github/workflows/zbirka.yml`, ~р.600).
- `concurrency` збірки на push: одна група `main`, `cancel-in-progress: false` — GitHub тримає одну запущену й одну очікувану, новіша очікувана витісняє старшу. CI іде ~35–60 хв, злиття частіші, тож кожна збірка до кінця застає новіший main зі зміненими paths → пропуск; «його збірка» так само застаріє. Це гіпотеза кореня: підтверди повним виміром запусків за 29.10 (усі push-запуски збірки: SHA, тривалість, підсумок кроку публікації).
- Зараз опубліковано 560fa388 — за частих злиттів знову застигне.

**Ціль (мірило).** За будь-якої частоти злиттів `build.txt` у `main` рухається вперед: кожна завершена зелена збірка push публікує, якщо її джерела новіші за поточний штамп (без силового push, без розсинхрону `index.html` ↔ `build.txt` ↔ штамп джерел); вікно без публікації обмежене однією тривалістю CI, а не числом злиттів. Доказ — відтворення голоду (стенд або повтор послідовності SHA за 29.10) ДО і ПІСЛЯ.

**Межі.** Тільки `.github/workflows/zbirka.yml` і потрібний йому прилад/стенд; не міняй читачів штампа в `аудит/адаптери/gemini/` (там відкриті #2211/#2212). Автоживий бере штамп `build.txt` (`queue_lanes.ps1`:290, 829; `wrapper_chain.ps1`:47) — семантику «штамп = SHA джерел, з яких зібрано `index.html`» зберегти. `workflow_dispatch` не запускати.
