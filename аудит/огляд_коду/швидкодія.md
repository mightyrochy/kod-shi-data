## 8. Варіанти «скомпілювати»: виграш на вимірах і ціна

**(1) Pyodide у Web Worker.** Зникне з головного потоку: long tasks 153–180 с за шлях; у зборі 83–107 с (93–95 % часу), найдовша
36–46 с (`запити`); екран «Палітра» 16–20 с; підйом 5.5–7.4 с. Лишиться: та сама обчислювальна робота (у Worker), отже **час збору майже
той самий** (оцінка ±5 %), плюс копіювання повідомлень: входи 2.06 МБ і виходи ≈ 14 МБ (`str`) на весь шлях — десятки мс (оцінка).
Python не торкається DOM (жодного `import js`/`pyodide.ffi` у 156 модулях), а JS ходить у Python через одну точку `містП`
(62 місця виклику) + 8 згадок `pyodide_показу` у `показ.html` → правка ≈ 100–150 рядків (оцінка) і 16 згадок у приладах
(`рв6_стенд.js`, `часи_збору.js`, `тест_показу.js`, `наскрізь.js`, `хід_5252.js`). Ризик для поведінки — низький (той самий Pyodide).
Поступливий режим `bridge.виклик_а`/`asyncio.sleep` у `оцінка_образу.py` стане непотрібним. Друга-третя Worker-копія могла б
паралелити код рук 1 і 2 (16–27 с кожна) — оцінка −15…−25 с збору ціною ще одного підйому й пам'яті Pyodide.

**(2) Заздалегідь скомпільований байткод / кеш.** Виміряно: імпорт bridge у Pyodide 1 938 мс → **417–633 мс** з .pyc
(compileall перед імпортом; компіляцій під час імпорту 0); у CPython 930 → 88 мс. Виграш ≈ **1.3–1.5 с раз на відкриття** (≈1 % шляху).
Ціна: .pyc 5.44 МБ проти .py 4.36 МБ, у zip (bz2) 2.32 МБ проти 1.03 МБ → **+1.3 МБ zip / +1.7 МБ base64 у index.html**;
крок збірки `python3.12 -m compileall -b` (MAGIC 3.12 `cb0d0d0a` — той самий рядок 3.12; для Pyodide 3.12.1 треба перевірити
живцем, оцінка); `-OO` розміру не змінює (2.317 МБ). stdlib Pyodide теж іде як .py: ще ≈ 0.3 с (власний час імпорту stdlib 327 мс).
HTTP-кеш Pyodide між відвідинами: `loadPyodide` 4.1 → 2.4–2.6 с і мінус 5.7 МБ мережі (на 10 Мбіт/с ≈ 4–5 с, оцінка) — дешево
(заголовки jsDelivr уже дають кеш; Service Worker додав би офлайн). Поряд дешевші за компіляцію: `Uint8Array.from(atob(…), cb)`
676 мс (заміна на `fetch(data:)`/`Uint8Array.fromBase64` — оцінка −0.6 с) і bz2 55 МБ XML 2.3 с + розбір XML 4.6 с на «Палітрі».

**(3) Гарячі ділянки в WASM (Rust) / TS.** Топ-10 функцій за власним часом = **29 % CPU** на всіх 127 викликах (CPython-семплер),
**127 рядків**: `річ_з_фото.членство_в_палітрі` 4.8 % (24 р.), `_морфологія` 4.1 % (8), `колір_простір_перетворення.de00` 4.0 % (22),
`силует_крої.обгортка` 3.7 % (34), `lch` 2.9 % (2), `_дуга_членство` 2.2 % (10), `soft` 2.1 % (2), `реєстри._є` 2.0 % (7),
`фід_фото._файл_фото` 1.8 % (8), `fit.ширина_на` 1.8 % (10). Але половина з них — сцена 6 (`річ_з_фото`), а не «Зібрати»; функції
крихітні й кличуться мільйонами (`lch` 5.8 млн, `dict.get` 52 млн), тож перехід Pyodide↔WASM на кожен виклик з'їсть виграш —
переносити довелося б цілі цикли (оцінка: сотні–тисячі рядків). Стеля виграшу ≈ 29 % × (1 − 1/k); для «Зібрати» менше. Ризик поведінки —
та сама колірна математика, що вже розходиться на 1 ulp (§5).

**(4) TypeScript для всього браузерного ядра.** У браузер їде **156 модулів, 56 223 рядки Python (52 705 рядків коду без
коментарів і рядкових літералів)**. Зникли б 13.7 МБ Pyodide, 8.9 с підйому, 1.3 МБ base64 модулів, і код став би в рази швидшим
(JIT V8 проти CPython-у-wasm; оцінка ≥5–10×, не міряно). Ціна — переписати 52.7 тис. рядків і всі Python-тести/гейти; ризик змінити
поведінку високий і вже доведений: навіть CPython↔Pyodide розходяться в 18/111 викликах; `Math` V8 — третій варіант libm, плюс інші
правила округлення, порядку словників, регулярних виразів.

**(5) Серверне ядро (CPython).** Зникне з телефона: 13.7 МБ Pyodide (5.7 МБ gz), 8.05 МБ base64 вантажу (91 % index.html → сторінка
≈ 0.77 МБ), підйом 8.9 с, усі заморожування (153–180 с long tasks). Код стане ≈ **1.9–2.1× швидшим** (3.12; 3.13 ще ≈ 11 %), збір
62.7 → 31.4 с CPU (відтворення). Додасться: 99 запитів bridge на збір і 127 на шлях — RTT 50–150 мс на послідовних кроках руки
(≈ 15 на ланцюгу руки 1 → 1–2 с, оцінка); обсяг: входи 2.06 МБ, виходи ≈ 14 МБ — виходи треба стиснути/обрізати (`запити` віддає
2.4–2.9 МБ); сервер: ≈ 31 с CPU на збір і ≈ 58 с на шлях з оцінкою — одне ядро тягне ~2 збори/хв (оцінка), каталог (прогрів 4.1 с)
мусить жити в теплому процесі; стан модулів (кеші `_пакет_каталогу`, `_база_прогону`) — прив'язка сесії. Поведінка зміниться там,
де libm (§5) — зате стане тією самою, що в CI.

## 9. Висновок: де справжнє вузьке місце

1. **Python-обчислення ядра в головному потоці**, а не компіляція і не моделі. На «Зібрати образи» код — 82–105 с (заглушка),
   78–99 с при хмарних затримках 2–15 с/виклик (60–70 % збору), сторінка заморожена до 46 с поспіль. Модель стає головною лише від
   ≈15–20 с на виклик або на ноутбуці з одним слотом (175.6 с, модель 141 с).
2. Усе, що можна «скомпілювати» без переписування (pyc, кеш Pyodide, швидший base64), дає **≈ 2–4 с на відкриття** (1–3 % шляху),
   жодної секунди збору.
3. Найбільший дешевий виграш — **не компіляція, а повторна робота**: бриф/простір рахуються 53/111 разів на 3/2 різних входи
   (≈ 58 % `від_моделі`, ≈ 20–30 с Pyodide на збір), плюс `запити` (25–40 с) один раз до будь-якого виклику моделі. Кешування брифу —
   правка Python без зміни поведінки (виходи повторів побітово рівні першому), її варто міряти першою.
4. Worker — правильний наступний крок для чуйності (знімає 100 % заморожувань, ≈ 100–150 рядків), але час збору не скорочує;
   серверне ядро — ×2 швидкості ціною мережі, сервера й зміни libm; TS/WASM — найдорожче й найризиковіше.
5. ЗНАХІДКА: CPython (CI) і Pyodide (жінка) дають різні палітри/пули на тих самих входах через libm (≤1 ulp у `atan2`, `cos`, `pow`).
