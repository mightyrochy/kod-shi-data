# CI за шляхами й Windows-стенди обгортки

База латок: `614635841a6c9e446a3450513749fadaaafc54b0` (`main`, названий адаптером запуску).
Гілка виконавця: `gemini/CI-шляхи-й-стенди-обгортки`. Захищені файли в ній не змінено;
їхні зміни подано лише латками за доповненням менеджера 27.10 12:53.

## Застосування

Застосовувати послідовно на базі:

```bash
git apply --check аудит/латки/CI-шляхи-й-стенди-обгортки/01-ci.patch
git apply аудит/латки/CI-шляхи-й-стенди-обгортки/01-ci.patch
git apply --check аудит/латки/CI-шляхи-й-стенди-обгортки/02-stendy.patch
git apply аудит/латки/CI-шляхи-й-стенди-обгортки/02-stendy.patch
```

| Латка | Файли |
| --- | --- |
| `01-ci.patch` | `.github/workflows/zbirka.yml`; новий `.github/workflows/obhortka.yml` |
| `02-stendy.patch` | `аудит/адаптери/gemini/перевірка/сценарії_прогону.sh`; нові `запустити_стенд.sh`, `перевірити_хеші.py` у тій самій теці |

У `zminy` два виходи: `produkt` для `джерела/**`, каталогу, `index.html`, `build.txt` і самого `zbirka.yml`;
`pravyla` для Markdown, приладу `джерела/правила.py` і самого `zbirka.yml`. Невідомий diff зберігає повний шлях.
Перейменування читаються як видалення й додавання; імена файлів передаються через NUL.
Легкий шлях перевіряє згортання дошки на PR і push. У `publish` лише узгоджено назву виходу й відповідні умови;
перенос публікації далі читає той самий список `push.paths` із YAML. До нього додано `index.html` і `build.txt`.

## Які задачі запускаються

Це висновок з `if:` і `paths`, перевірений локально точним Bash-кодом класифікатора на merge-комітах (`шляхи.txt`).
GitHub Actions у цій сесії не запускався; зелений CI майбутнього PR має підтвердити перевірка.

| Зміни PR | `zminy` | `perevirka`, `rozdily` | `pravyla` | `zbirka` | Windows `obhortka` | `publish` |
| --- | --- | --- | --- | --- | --- | --- |
| Лише скрипти `аудит/адаптери/gemini/**` | легкий шлях + дошка | пропущено | пропущено; за наявності `.md` — звіт | checkout + Python, важкі кроки пропущено | усі 8 стендів і хеші | пропущено |
| `джерела/bridge.py` | продуктовий шлях | обидві повністю | пропущено; документи/прилад правил додають звіт | усі кроки після успішних перевірок | процес не запускається | пропущено |
| Лише документи поза `джерела/` й обгорткою | легкий шлях + дошка | пропущено | звіт правил | checkout + Python, важкі кроки пропущено | процес не запускається | пропущено |

PR із **застосованими латками цього наряду** змінює обидва workflow: `zminy`, `perevirka`, `rozdily`,
`pravyla`, усі кроки `zbirka` та Windows-стенди запускаються; `publish` пропущено, бо це PR.
PR, який містить лише ці файли латок і два уточнення правил, сам латок не застосовує: легкий шлях + звіт правил,
без нового Windows-процесу. Це пакет для наступної сесії, а не вже змінений CI.
На push `main` обгортки запускається лише Windows-процес; продукт/дошка запускають `zbirka.yml` згідно з `push.paths`.

## Прогони

`стенди.txt` містить команди та вивід. Спільна команда кожного окремого кроку CI й ноутбука:

```bash
bash аудит/адаптери/gemini/перевірка/запустити_стенд.sh сценарії_claude.sh
```

Так само запускаються всі інші `сценарії_*.sh`. Без аргументів `сценарії_прогону.sh` виконує 14 описаних у ньому випадків;
режим з аргументами збережено для сусідніх стендів. Запускач перевіряє код стенда, код `tee`, явні ✗/FAIL/ПОМИЛКА
і наявність перевірок; записує числа у `$GITHUB_STEP_SUMMARY`. Контроль зі стендом, що друкує ✗ і повертає 0,
дав очікуваний код запускача 1. У Windows-процесі кожен стенд має окремий крок, наступні виконуються і після відмови
попереднього; будь-яка відмова робить задачу червоною.

Хеші звіряє окремий крок `python аудит/адаптери/gemini/перевірка/перевірити_хеші.py`:
маніфест = таблиця = SHA-256 `git show HEAD:<шлях>`; CRLF у блобі — відмова.
Перед checkout CI вимикає `core.autocrlf`, щоб Bash отримав LF; спільне `середовище.sh` на Windows обирає
PowerShell 5.1 через обгортку з `ExecutionPolicy Bypass` і створює `.cmd`-заглушки в ASCII-теці.

Незалежна перевірка диффу іншим постачальником і застосування латок короткою сесією Claude — наступні кроки наряду,
які не виконує ця сесія. Зміни договору перевірки — звичайними комітами гілки.
