# Обгортка: залежності бандла

База: `1f1d5b4c257f1032f1feb777266878d006c3d761`.
Код змінюється лише в окремому тимчасовому дереві; у гілку подається латка.

Три початкові бандли доступні в `C:/Users/Public/gemini/out`; їхні заголовки та
`git bundle verify` у клоні виконавця — `початкові-бандли.txt`.
Кожен вимагає рівно свій `start`: `e60e6233…`, `6374e62e…`, `dfd49736…`.
Це локальні злиття гілок перевірки, а не гарантовано опублікована база.
У клоні виконавця ці об'єкти є, тому verify має код 0; історичне сховище
публікатора та його `inbox` із профілю власника під ізольованим `gemini` недоступні.
Ці результати не видаються за verify в історичному сховищі публікатора.

На локальному стенді справжні `Complete-Status` і `Publish-Bundle` відтворили
обидва механізми: приватний `start`, який уже містить злиття main, та злиття
новішого main після опублікованого `start`. В обох випадках публікатор має коміт
позначки, проте бракує виключеного коміту: verify = 1, `BUNDLE_INVALID`, гілку не
пересунуто. Точний вивід — `до.txt`. Перший випадок відповідає залежностям усіх
трьох наявних бандлів; другий перевіряє окремо гіпотезу наряду про свіжіший main.

Виправлення: `Complete-Status`, спільна для agy, Codex і закриття перерваного
прогону, виключає лише `Status.marker`. Коміт позначки публікатор отримує з origin
разом із чергою; усі неопубліковані злиття та коміти main після цієї бази входять
до бандла. Так не потрібне припущення про наявність `start` чи однаковий main.
Це інкрементальний бандл від опублікованої бази, а не повна історія репозиторію.

`Publish-Bundle` зберігає перевірку Git і всі наступні відмови; при невдалому
verify без `-q` пише його код та обидва потоки у локальний `publish.log`, а диспетчерові, як і
раніше, передається тільки код `BUNDLE_INVALID`. Це дасть конкретний SHA
відсутньої передумови, якого раніше в журналі публікатора не було.

На тій самій пробі після правки: **private-start / new-main: BUNDLE_INVALID → OK**.
Кожна публікація перевіряється за SHA у локальному origin, не лише за кодом
`Publish-Bundle`; режим `DryRun` не використовується. Також пройшла доробка
опублікованого start, а `REF_MISMATCH`, `SECRET`, `GITHUB_DIR`, `WRAPPER_FILES`
не пересувають опублікованої гілки. Старий неповний бандл відхиляється з точним
SHA відсутньої передумови в журналі; `-q` прибирав цю діагностику з обох потоків.
Усього остаточна нова проба: **8 ✓ / 0 ✗**.

Це власна перевірка виконавця на стенді. Робочі задачі планувальника не змінено;
виробничий прогін після застосування латки залишається перевірці й диспетчерові.

Під час повного прогону виявлено залежність стендів від справжнього
`C:/ProgramData/gemini-wrapper/selfupdate.ready`: доставка отримувала зайві
рядки `UPDATE_ACL`, а стенд здоров'я — `UPDATE_MAIN` від своєї заглушки Git.
Виправлено саме ізоляцію стенда: `side.ps1` дає публікатору тимчасовий
`UpdateRoot`, якщо його не задав сценарій; прямий виклик публікатора у
`сценарії_здоровя.ps1` теж передає власну теку. Явні теки сценаріїв
самооновлення збережено; виробничі перевірки ACL не змінено.

Усі **12 `сценарії_*.sh`: 294 ✓ / 0 ✗**, кожен із кодом 0.
Остаточні підсумки й час — `стенди/результати.json`, повні журнали — поруч.
Попередні провали через зовнішню теку самооновлення — `стенди/до-ізоляції/`,
проба неповної діагностики — `стенди/до-діагностики/`.
У журналах нормалізовано лише переноси рядків і кінцеві пробіли.

Відтворення комплекту на окремому дереві після застосування латки:

```powershell
python аудит/латки/обгортка-bundle-invalid/прогнати_стенди.py <дерево> <журнали>
```

Одна латка — `01-база-бандла.patch`, SHA-256:
`58E22D8C83A64705732A7553F1289A85B454B285794F844563E4B4B31BB296F5`.
На чистій базі `1f1d5b4c257f1032f1feb777266878d006c3d761`:

```powershell
git apply --check аудит/латки/обгортка-bundle-invalid/01-база-бандла.patch
git apply --index аудит/латки/обгортка-bundle-invalid/01-база-бандла.patch
python аудит/адаптери/gemini/перевірка/перевірити_хеші.py
```

Для Windows потрібен checkout із LF (`core.autocrlf=false`); латка зберігає точні
байти через власний `.gitattributes`. Перевірка застосування — код 0; після
застосування дифф побайтово дорівнює латці, усі 9 хешів — 0 ✗. Протокол —
`застосування.txt`. У тій самій латці оновлено обидва хеші скриптів у маніфесті
та документації. Захищені шляхи робочої гілки не змінювалися.
