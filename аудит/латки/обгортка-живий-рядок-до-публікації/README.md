# Перевірка тіла PR до публікації

База латки: свіжий `origin/main` на `2a7e1bf84b3c9cb86321958c47d1fc362f0d602f` (звірено `git fetch origin main`).
Наряд: обгортка-живий-рядок-до-публікації, номери 12360–12363.
Зміни захищених файлів обгортки й CI містяться лише в `зміни.patch`.

`Get-LiveAfterLines` лишається одним читачем для планувальника, CI, приймання звіту й публікації.
Перенесення одного абзацу склеюються до розбору; порожній рядок, пункт, заголовок, цитата й підпис поля
не можуть дописати неповний рядок. Прийнятий звіт із вадою отримує один хід того самого виконавця,
окремий від `MaxNudges`. Повторна вада дає BLOCKED. Перед POST і PATCH вадний рядок замінюється
поясненням із причиною та оригіналом; тіло закінчується блокером, CI читає його без помилки формату.

Усі записи тіла проходять `Complete-EngineDrafts`: створення чернетки, автоперевірка,
`перевірка-<PR>` та оновлення наявного PR. `Get-Line` ставить запит і для опублікованого блокера;
для вадного тіла канал доставки несе `LIVE_AFTER_INVALID_PUBLISHED`, повний текст причини є в тілі й журналі.
Перед PATCH публікатор окремим GET читає чинне тіло: список PR міг передувати допису перевірки.
Спільна `Merge-LivePublicationBody` зберігає сцени чинного тіла й усі різні питання до тієї самої сцени
через ` ; ` в одному рядку. Однакові питання не дублюються при повторі. Інші абзаци старого звіту не повертаються.
Збій GET або PATCH зберігає запит для повтору; вадна сцена чинного тіла також проходить пояснення з блокером.
Звіт перевірки без рядків дошки й далі лишається гілкою, як визначено договором перевірки.
У перерваного прогону немає прийнятого звіту для повторного ходу: публікатор застосовує той самий
читач і зберігає ваду в тілі з блокером.

Обидва планувальники перед запуском додають модель позначки в текст автоперевірки та
`перевірка-<PR>`. Інсталятор власника також отримує й звіряє `queue_lanes.ps1` для публікатора;
маніфест і таблиця SHA-256 оновлені разом зі скриптами.

## Застосування й перевірка

Диспетчер застосовує латку в окремій дозволеній гілці від бази. З кореня дерева:

```powershell
git apply --check аудит/латки/обгортка-живий-рядок-до-публікації/зміни.patch
git apply аудит/латки/обгортка-живий-рядок-до-публікації/зміни.patch
powershell.exe -NoProfile -ExecutionPolicy Bypass -File аудит/адаптери/gemini/перевірка/сценарії_живий_до_pr.ps1 -SourceDir аудит/адаптери/gemini
python аудит/адаптери/gemini/перевірка/перевірити_хеші.py --диск
```

Новий стенд доданий у частину 3 матриці `obhortka.yml` рівно один раз.
Спільний запускальник знаходить його автоматично; збирач звіряє єдиність результату.
Для виміру ДО запустити цей самий стенд із застосованого дерева, але передати
`-SourceDir <дерево-бази>/аудит/адаптери/gemini -Phase ДО`.

## Доробка за перевіркою #2831

Розділ 6 того самого стенда відтворює PATCH з новим звітом без сцен і сценою, яку перевірка додала
до чинного PR. На попередній латці `975a0bed1b36f97822492991a16058a39381e214` сцени зникали;
для відтворення використано файл латки з батьківської гілки до доробки.
У класі записів тіла обгорткою одна функція `Complete-EngineDrafts`; шляхів PATCH повз
збереження сцен ДО 1 → ПІСЛЯ 0. POST, BLOCKED_PUBLISHED і обидві форми перевірки використовують її ж.

| Проба | ДО доробки | ПІСЛЯ |
|---|---|---|
| Сцени перевірки після PATCH | 1 → 0 | 1 → 1 |
| Чинне тіло відрізняється від списку PR | сцена губиться | окремий GET зберігає сцену |
| Дві сцени в чинному тілі, одна в коміті | одна губиться | дві сцени, без дубля |
| Одна сцена з різними питаннями | питання перевірки губиться | один рядок, обидва питання |
| Повтор і відмови API | сцени не захищені | GET/PATCH не гублять запит; повтор зберігає сцени |

ДО доробки: 48/48 тверджень (47 попередніх і підтвердження втрати 1 → 0).
ПІСЛЯ: 60/60, включно з усіма трьома формами гілки, перенесенням чинної сцени й вадою старого тіла.
Стенд після застосування оновленої латки до окремого дерева бази також проходить 60/60.

```powershell
# Стенд із нової латки; SourceDir — дерево попередньої латки 975a0bed1.
```
