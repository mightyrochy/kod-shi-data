# Ланцюг — лише живі PR

База латки: `023d001e07df71927fb7a684584993d12cf4fd28` (`origin/main` робочого дерева обгортки).
Наряд походить із `678316b051e7983d391f60d57707303f30c90b47`; обрана обгорткою гілка збережена.
Код змінено в окремому `git worktree` поза репозиторієм. У цій гілці немає прямих змін
`.github/` чи `аудит/адаптери/gemini/`; застосування латки й публікація — за диспетчером та обгорткою.

## Що змінено

`queue_lanes.ps1` читає публічний GitHub REST без входу, моделі й нових секретів. Обидва планувальники
перевіряють номер PR, стан `open`, точний SHA, автора, репозиторій і базу в процесі наряду,
який уже отримав вільний слот, безпосередньо перед моделлю. Закритий PR, інша голова чи звіт автоперевірки закривають
позначку як `DONE … STALE`. Публікатор знає цей код і доставляє один службовий рядок
`GEMINI ОБГОРТКА: ЗАБЛОКОВАНО <гілка> STALE`; повтор не створює нового рядка.
Віддалені позначки не видаляються, тому це поширюється й на 44 вже поставлені.

Планувальники не викликають API під час обходу черги. Звірка всередині процесу наряду перед
викликом моделі захищає від зміни PR між постановкою й стартом. Збій API чи неповна відповідь
повертають узяту позначку в `WAIT` на 120 секунд зі збереженням retakes і голови продовження.
Кінцевого `REVIEW_API`, звіту диспетчерові чи виклику моделі при цьому немає.
Закриття PR після останньої звірки вже запущений прогін не перериває.

`review_hours` у `ланцюг.json`: ціле число 1–168, типово **24 години**, старий конфіг без поля також
отримує 24. Добове вікно захоплює поточну роботу після паузи ноутбука, не охоплюючи архів 15–26.10.
Сім діб — явна верхня межа налаштування, а не необмежене повернення всіх давніх чернеток.

Перший прохід нової версії створює UTC-межу встановлення політики й знімок голів у `chain.json`.
Допускається PR, створений після цієї межі, спостережена зміна SHA або початковий SHA з часом
committer у включному вікні `[зараз − N годин, зараз]`. Майбутні дати відкидаються.
Початкове рішення зберігається з SHA; нова спостережена голова допускається навіть зі старим комітом.
Вікно використовується лише для невідомої голови: вже виявлена після встановлення робота не губиться
через перезапуск чи затримку API. `updated_at` PR не використовується, оскільки його освіжають і коментарі.
Час комітера не є точним часом push: невідома до першого знімка голова зі старим комітом за межами
вікна очікуватиме нового SHA. Втрата локального стану починає нову базову лінію; віддалені позначки
й lease зберігають захист від повторів.

Давність обмежує нову постановку. Вже поставлена позначка відкритого PR з точним SHA лише через
сплив доби не скасовується. Звіти `*/автоперевірка-*` не ставляться ніколи; цей фільтр уже був
у базовому `main` і збережений. Додано відсікання вже наявних позначок таких звітів перед запуском.

Джерела полів API: [PR](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request),
[коміт точного SHA](https://docs.github.com/en/rest/commits/commits#get-a-commit).

## Проба ДО → ПІСЛЯ

`проба.ps1` підвантажує справжні ланцюг, планувальники, виконання наряду й публікатор.
Віддалений git локальний; відповіді API та функції виклику моделей підмінені. Лічиться вхід
у `Invoke-Agent` / `Invoke-Claude`, а не лише кількість позначок. Платних запитів немає.

У кожній смузі три позначки вже існують: закритий PR, змінена голова й автозвіт. Ланцюг окремо
одержує давній PR зі свіжим коментарем та живий PR. Це відтворює залишки черги й нову постановку,
не приписуючи базовому `main` відсутнього в ньому дефекту фільтра автозвітів.

| смуга | ДО, запусків із п’яти | ПІСЛЯ |
|---|---:|---:|
| Codex | 5 | 1 |
| agy | 5 | 1 |
| Claude | 5 | 1 |

Докази: `журнали/ДО.txt`, `журнали/ПІСЛЯ.txt`, `результати-проби.json`.
Після виправлення додатково звірено три `STALE`, відсутність повторів, прийняття кодів публікатором,
відкладення при 503 та запуск тієї самої позначки після відновлення API.

Новий `сценарії_живих_pr.sh` повторює це мірило ПІСЛЯ у всіх трьох смугах. У базі було 11
`сценарії_*.sh`; з цією пробою стало 12. Чинний стенд ланцюга доповнений вимірами часової межі,
нового PR зі старим комітом, спостереженої зміни SHA та збереження рішення після перезапуску.

## Застосування й повтор

У чистому дереві вказаної бази:

```powershell
git apply --check <шлях-до-латки>/01-живі-pr.patch
git apply --index <шлях-до-латки>/01-живі-pr.patch
python аудит/адаптери/gemini/перевірка/перевірити_хеші.py
```

У Git Bash — послідовно всі `аудит/адаптери/gemini/перевірка/сценарії_*.sh`.
Або з Windows через збережений збирач журналів:

```powershell
python <шлях>/перевірка.py стенди --дерево <дерево-з-застосованою-латкою>
```

Безпосереднє порівняння зі збереженою пробою:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File <шлях>/проба.ps1 -SourceDir <початкова-обгортка> -Phase ДО
powershell -NoProfile -ExecutionPolicy Bypass -File <шлях>/проба.ps1 -SourceDir <обгортка-з-латкою> -Phase ПІСЛЯ
```

Синтаксис, хеші, результати всіх сценаріїв і чистий `git apply --check` зафіксовані поруч із латкою.
Підсумок: **12/12 сценаріїв — код 0, 0 ✗** (`результати-стенди.json`); **9/9 хешів**;
**21 PowerShell-файл — 0 синтаксичних помилок**; `git apply --check` — **0**.
Перший прогін виявив залежність стендів доставки й здоров’я від установленого `UpdateRoot`:
наявний `selfupdate.ready` додавав сторонні рядки оновлення, а підробний git здоров’я давав `UPDATE_MAIN`.
Спільний `side.ps1` і прямий виклик у стенді здоров’я тепер передають власний неактивний корінь
під тимчасовою текою стенда. Явно переданий тестом `UpdateRoot` зберігається, перевірка
самооновлення не вимикається. Первинні червоні журнали збережені поруч із повторними.
Хеші п’яти змінених виконуваних файлів оновлені разом у `m9v/хеші.psd1` і таблиці `НАЛАШТУВАННЯ.md`.
Самооновлення, встановлені копії та живу чергу ноутбука ця сесія не змінювала.
Стенд є власною перевіркою виконавця; незалежне приймання та застосування лишаються за наступною роллю.
Нових вад поза мірилом наряду не знайдено.

## Завершення після продовження

Повторна звірка `turn2.md` підтвердила застосування латки до записаної бази, 9/9 хешів
і пробу ПІСЛЯ у трьох смугах. Подробиці — у `продовження.txt`.
Незакомічений журнал `доробка-1969/ci-журнал-122406308522.txt` побайтово збігався з `HEAD`,
але його збережені CRLF суперечили чинному `* text eol=lf`. Через це `Test-Report`
відхиляв завершення за умовою `Dirty -eq 0`. Нормалізовано лише 864 перенесення рядків;
`git diff --cached --ignore-space-at-eol --exit-code` перед додаванням цього запису дав 0.
Зміст історичного журналу збережено. Це усуває перешкоду публікації вже готової латки.

## Спроба 2: бюджет API й збереження спроби

Продовжено гілку від `9b7850302`. ДО для цього виміру — попередня латка з цієї голови,
накладена на записану базу; ДО для мірила 5/5 — базовий адаптер без латки.
Встановлену обгортку, живу чергу й нормалізацію CRLF журналу доробки-1969 збережено.

Єдина REST-звірка стоїть у `Invoke-Task`: вимкнена смуга, зайнятий слот і майбутній `WAIT`
не роблять запитів. Успішні відповіді не кешуються, тому кожен запуск звіряє поточний PR/SHA.
Усі три смуги й обидва облікові записи користуються `review-api.json` і `review-api.lock`
у чинному спільному `$LaneDir`. Перед мережею під замком резервується одна з **30** подій
рухомого вікна **3600 секунд**. До бюджету входять також 403/429, тайм-аути й падіння процесу.
Мережева відмова додає спільну паузу **120 секунд**; зайнятий замок, пошкоджений стан чи
вичерпана межа також відкладають позначку. Перезапуск процесу бюджету не обнуляє.

30 із публічних 60 запитів/год — свідома половина бюджету, спільна для планувальників,
а не по 30 на кожен процес чи смугу. Інші 30 лишаються для стороннього читання й запитів ланцюга;
це не гарантія для всього спільного IP. Чинний ланцюг читає PR і дату коміту через `gh api`
публікатора, а не через новий публічний REST: список сторінками по 100, дату незнайомого SHA —
один раз перед збереженням рішення у `chain.json`. Якщо залишок IP вичерпаний іншими читачами,
відмова API лише відкладає наряд. Пропускна здатність цієї звірки — до 30 запусків/год;
піковий хвіст черги очікує наступного рухомого вікна без витрати спроб чи квоти моделі.

`бюджет.ps1` виконує справжні `Start-Markers` і `Invoke-Task` з підмінами git IO, REST і моделей:
30 позначок (по 10 у кожній смузі), 60 хвилинних проходів, перші 30 зі зайнятим слотом.
ДО: Codex 320 + agy 320 + Claude 50 = **690 запитів/год**. Claude перериває обхід на першому
зайнятому слоті, тому його внесок менший. ПІСЛЯ: **30 запитів/год**, усі 30 живих позначок
доходять до моделі; 31-й запит відкладається, також в окремому процесі; після рухомої години
нова звірка дозволена. Годинник стенда підмінений, реального годинного чекання немає.

Для кожної смуги окремо 403, 429 і мережевий збій подаються вже після claim у `Invoke-Task`:
спалених спроб **9 → 0**. Навіть при `retakes=5` позначка повертається у `WAIT` з тими самими
п’ятьма поверненнями й після відновлення запускає модель. Голова продовження Codex/agy зберігається.
Повний вимір — `журнали/бюджет-ДО.txt`, `журнали/бюджет-ПІСЛЯ.txt`, `результати-бюджет.json`.
Ця проба входить у чинний `сценарії_живих_pr.sh`; загальна кількість сценаріїв лишилася 12.

```powershell
python -X utf8 <шлях>/перевірка.py бюджет --дерево <дерево-з-новою-латкою> --база <дерево-з-попередньою-латкою>
python -X utf8 <шлях>/перевірка.py проби --дерево <дерево-з-новою-латкою> --база <дерево-бази>
python -X utf8 <шлях>/перевірка.py стенди --дерево <дерево-з-новою-латкою>
```
