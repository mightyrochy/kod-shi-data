Причина узгодження: початкова #1949 не застосовується після #1945 у `m9v/хеші.psd1` та `НАЛАШТУВАННЯ.md`:

в контексті обох файлів з `CEBCDD8FFEAFCDF29D9B4F5F624F00E8C8AE9A3811B49E87D3EB6B9B992C24ED`
на `3550085176F339BA00B1D1C28391AC585B0959128335D193601734261D00085B`.
Виробнича поведінка #1949 збережена. SHA-256 узгодженої латки:
`42d5ea38eb98b32c8615de1f58df93c4db066dbd1dbc6877f8f7b036587af15a`.
Дерево після залежностей: `c4ff3884ebe0dcf8a48c96b8bdc212d29e0e8c3a`.

Перед кожним застосуванням — `git apply --check`, потім `git apply --index`.
Робоча копія має LF (`core.autocrlf=false` до checkout); `.gitattributes` поруч зберігає точні байти латок.
Після залежностей застосовується `01-самооновлення-й-ланцюг.patch`. Хеші в ній перераховано для стану після всіх трьох нарядів.

Два постійні шаблони `аудит/наряди/автоперевірка.md` та `автоживий.md` доставляються звичайними файлами цього PR.
Їх треба зберегти в main перед увімкненням ланцюга. Власний одноразовий наряд Е0 прибирається після виконання.

Латки застосовує сесія Claude після перевірки іншим постачальником. Потім та сама сесія під обліковим записом
власника один раз запускає `m9v/3_самооновлення.ps1` з перевіреного main. Він використовує наявне право запису
в ProgramData, не змінює ACL чи задач і не потребує адміністратора, пароля або нового входу.
Попередні встановлені скрипти не містять механізму оновлення: без цього одноразового переходу вони не зможуть
підхопити першу версію. Далі оновлення після злиття виконує сама обгортка.

Повні команди, результати всіх стендів, перелік файлів Е0 і межі приймання доповнюються після завершення прогону.
