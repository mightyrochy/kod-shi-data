Знімок API знято 04.11.2026 UTC. Латка ще не застосована до workflow: її застосовує диспетчер за М.9-Г.

## 12830: увесь обсяг за 31.10–03.11 UTC

Вибірка — **усі 868 запусків `zbirka.yml`**, створених від `2026-10-31T00:00:00Z` до
`2026-11-03T23:59:59Z`, включно з усіма повторними спробами: **871 спроба, 7624 job**.
Усі сторінки списку запусків і jobs прочитані; кількості звірено з `total_count`, дублікати ID заборонені.

## Що доведено про причину

Механізм зайвого завантаження встановлено за закріпленою версією action:
[`git-source-provider.ts:172`](https://github.com/actions/checkout/blob/34e114876b0b11c390a56381ad16ebd13914f8d5/src/git-source-provider.ts#L172)
за `fetchDepth <= 0` викликає
[`getRefSpecForAllHistory`](https://github.com/actions/checkout/blob/34e114876b0b11c390a56381ad16ebd13914f8d5/src/ref-helper.ts#L69),
який додає `+refs/heads/*:refs/remotes/origin/*` і всі теги. Отже, чотири checkout отримують усі гілки,
хоча жоден їхній наступний крок не потребує посилань на чужі незлиті гілки.

Повний вимір показує: **63 із 81** тайм-ауту настали безпосередньо в checkout. Ще 7 — у звіті правил після
checkout тривалістю 425–566 с, 7 — у збірці бази після checkout тривалістю 2070–2250 с.
Решта 4 — у залежностях браузера після checkout 74–89 с: їх цей механізм не пояснює; випадок залежностей
браузера вже названо в коментарі workflow як 12114.

Гіпотеза: збільшення обсягу чужих гілок пояснює зростання затримок. **Історичного ряду числа гілок,
байтів передачі, швидкості мережі й навантаження runner немає**, тому залежність часу від їхнього розміру
не встановлена й усі 81 тайм-аут одній причині не приписані.
Поточний `git ls-remote --heads --tags origin` о `2026-11-04T02:32:14Z` дав 4159 гілок, 0 тегів
([refs.json](refs.json)); це не ретроспективний замір. Команда `git ls-remote origin | wc -l` з наряду
сама собою не відокремлює гілки від інших refs.

## 12831: що містить checkout.patch

- Усі чотири `fetch-depth: 0` замінено на `fetch-depth: 1`.
- Після кожного — однаковий виклик нового `.github/scripts/checkout-history.sh` із латки.
  Скрипт явно отримує SHA голови, `BASE_REF` та `refs/heads/main:refs/remotes/origin/main`;
  `--no-tags --no-recurse-submodules`, без wildcard і без default-fetch чужих гілок.
- У неглибокій копії використано `--unshallow` **з цими явними refspec**; у повній — звичайний явний fetch.
  `HEAD` не перемикається, база та спільний предок перевіряються.
- Повна історія цих refs навмисно збережена: проби поділу читають `ac8c2ca`, `b993a38`, `d1dbd9a` та інші
  давні бази; `аудит/проби/звірки_Е1.js` читає `7bf892f1e7de2f17e063e9d86c08bec17ccf92ce`, а
  `правила.py` читає історію від `8b20ab7`. Зупинка історії на недавньому спільному предку прибрала б цей вхід.
  API `/compare/{ref}...067d98cc1f43782566e8b10117411a898a28b4d7` перевірено для всіх 13 давніх баз
  проб поділу, звірок Е1 і звіту правил: усюди `status=ahead`, `merge_base=base`, тобто це предки main;
  [історичні_бази.json](історичні_бази.json) зберігає повні SHA й відповіді порівнянь.
- `persist-credentials: false` збережено. Для явного fetch токен передано через середовище процесу Git;
  до `.git/config` він не записується.

Сканування всіх `.github/workflows/*.yml` знайшло рівно ці 4 випадки `fetch-depth: 0`;
інших завантажень усіх гілок не знайдено. Звірки, тести, пороги, матриця й часові межі залишені.
У робочому репозиторії `.github/` та `аудит/адаптери/gemini/` не змінено.

## 12832: локальне мірило ДО → ПІСЛЯ

`git apply --check аудит/латки/CI-checkout-усі-гілки/checkout.patch` проходить на базовому дереві.
`перевірити.py` витягує shell-скрипт **зі створеної латки**, перевіряє `bash -n` і виконує його
на копіях контрольованого Git-репозиторію. В історії є давній файл, розгалужені main/PR, тестове злиття,
окрема незлита гілка з великим blob і тег на неї; remote.origin.fetch навмисно має wildcard.

ДО: refspec старого action отримує чужу гілку, її commit, великий blob і тег.
ПІСЛЯ: **0 чужих гілок, 0 їхніх commit/blob, 0 тегів**; доступні незмінена голова, точна база,
`origin/main`, спільний предок і файл давнього предка. Перевірено PR merge, PR head, push,
порожній BASE_REF, нульовий BASE_REF, окремо шлях із тестовим токеном — кожен двічі,
спочатку на неглибокій, потім на вже повній копії. Заголовок автентифікації не залишається в конфігурації.
Результати й тривалості — [локальна_перевірка.json](локальна_перевірка.json);
це час локальних фікстур, а не обіцянка часу реального checkout.

За уточненням диспетчера від 04.11 01:55 зелені 10 шматків Pyodide, решту jobs і час реального
checkout після застосування латки вимірює **диспетчер**. Тут цей CI не запускався й успішним не оголошується.
Йому слід рахувати разом початковий checkout та новий крок отримання історії: перенесений fetch
не можна приховати з мірила ≤180 с.

## Як відтворити

Із кореня репозиторію, PowerShell; Python 3.11+ і Git Bash:

```powershell
python аудит/латки/CI-checkout-усі-гілки/виміряти.py "$env:TEMP/checkout-api"
python аудит/латки/CI-checkout-усі-гілки/виміряти.py "$env:TEMP/checkout-api" annotations
python аудит/латки/CI-checkout-усі-гілки/виміряти.py "$env:TEMP/checkout-api" summary
python аудит/латки/CI-checkout-усі-гілки/перевірити.py 'C:/Program Files/Git/bin/bash.exe'
git apply --check аудит/латки/CI-checkout-усі-гілки/checkout.patch
```

Повний збережений знімок — [api.json.gz](api.json.gz): відповіді запусків, усі jobs і `steps[]` усіх спроб,
усі анотації невдалих jobs. SHA-256: `606fec449cd8dcda6ed59a851c18e62ef0c9f0b05fe2407a96c208bb489ef152`.
Він дозволяє повторити підрахунок **без мережі** після прибирання тимчасової теки обгорткою:

```powershell
python аудит/латки/CI-checkout-усі-гілки/виміряти.py аудит/латки/CI-checkout-усі-гілки/api.json.gz summary
```

Машинний підсумок із ID тайм-аутів і десятьма найдовшими checkout — [числа.json](числа.json).
API: `/actions/workflows/zbirka.yml/runs?created=…`, `/actions/runs/{id}/attempts/{attempt}/jobs`,
`/check-runs/{id}/annotations`; усюди `per_page=100`, усі сторінки через `gh api --paginate --slurp`.

Нових вад поза мірилом не знайдено. Батарея продукту тут не є мірилом: зміни передані лише латкою CI,
без змін коду продукту; реальні перевірки цього workflow залишаються обов'язковими після її застосування.
