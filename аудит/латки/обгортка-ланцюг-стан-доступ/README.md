# 13074–13076: доступна діагностика збоїв стану — доробка 1

Спроба 2 виконує доробку диспетчера від 05.11 05:25 UTC. Причина інцидентів за 04–05.11 залишається
невстановленою: доступу до `publish.log` не повторювали, ACL й обліковий запис не змінювали. Початкові пункти
13074–13076 (вимір причини, її виправлення й приймання після встановлення) залишаються наступній спробі.
Дослівний наряд цієї спроби — `НАРЯД-доробка-1.md`; звіт попередньої спроби збережено нижче.

## Латка

База — `main@63fdbbdea8c87d4220594844fbe7749ee900b0ea`, зазначена обгорткою. Файли адаптера в цій базі
збігаються з файлами початку продовженої гілки. Основне робоче дерево адаптера й `.github/` не змінювалися:
усі зміни гілки містяться в цій теці. `зміна.patch` застосовує диспетчер після огляду диффу:

```powershell
git apply --check --index аудит/латки/обгортка-ланцюг-стан-доступ/зміна.patch
git apply --index аудит/латки/обгортка-ланцюг-стан-доступ/зміна.patch
```

`Write-ChainFailure` і `Get-BadLine` дописують діагностику до приглушення повторів у
`C:\Users\Public\gemini\out\state-failures.jsonl` (за іншого `OutDir` — у цю теку). Наявність і доступність
цієї теки перевірено під `gemini`; `Get-Acl` показав власника `DESKTOP-6N11SA4\gemini` та успадкований доступ
для адміністраторів, інтерактивного й пакетного входу. Нових дозволів не потрібно. Цей `.jsonl` не входить
до вибірки станів `*.json` публікатора.

Один JSON-рядок містить UTC події, код, причину, повний шлях, тип об’єкта, власника, ACL у SDDL, час останнього
запису, повний .NET-виняток, стек PowerShell і позицію. Відмови отримання метаданих зберігаються окремо;
порожні поля не означають відсутності об’єкта. Невалідний формат без початкового винятку отримує
`InvalidDataException` із причиною перевірки. Режим `StatusOnly` зберігає читання без побічних ефектів.

Читання стану у `wrapper_chain.ps1`, включно з читачем позначок обох смуг, зберігає точний шлях у контексті
початкового винятку. У рядку `CHAIN_FAILED` він передається суфіксом `ШЛЯХ "<JSON-шлях>"`; шаблон доставки
узгоджено з цим форматом. Стек залишається в журналі. Старі форми рядка приймаються, довільні хвости й
керівні символи відхиляються. Хеші двох змінених модулів оновлено в маніфесті й таблиці налаштувань.
Рішення UNKNOWN/NEW не змінювалися; первинний `CHAIN_FAILED` сам собою не доводить переривання проходу.

## Відтворення

Середовище: Windows PowerShell 5.1, Python 3.12, Git Bash; робочі копії й TEMP/TMP/TMPDIR — лише в теці
поточного завдання. Скрипт `підготувати.py <тимчасове-дерево>` відтворює латку на чистій зазначеній базі;
він відмовляється змінювати основне дерево. `прогнати.py <тимчасове-дерево> [імена стендів]` зберігає команди,
коди та повний вивід у `стенди/`.

Новий стенд у латці — `перевірка/сценарії_діагностики_стану.ps1 -SourceDir <тека адаптера>`. Він використовує
справжні файлові операції: винятковий замок файла й теку замість файла, без змін ACL. Окремо звіряє
STATE_INVALID зайнятого файла, пошкодженого JSON і невалідного формату, приглушені повтори та читання StatusOnly.
Значення власника, ACL й часу звіряються з файловою системою; вихідний файл проходить справжній Read-OutboxFile.

Перший запуск наявного стенда повторів дав два провали: його підміна кешу залишала лише Get-MarkerState,
прибираючи функції ключа й шляху, потрібні для діагностики. Підміна тепер зберігає ці функції; очікування
доповнено суфіксом шляху. Початковий вивід і коди збережено в `первинні-стенди/`.

Підсумкове мірило на базі `63fdbbdea8c87d4220594844fbe7749ee900b0ea`: **ДО — 19 провалів, код 1;
ПІСЛЯ — 47 успішних перевірок, 0 провалів, код 0** (`до.log`, `після.log`). Перевірено застосовність
латки до чистої бази через `git apply --check --index`, саме застосування й зворотну перевірку з індексом;
перевірки ПІСЛЯ виконано на дереві, отриманому цим застосуванням, а не лише на файлах генератора.

Повна батарея — 27 окремих запусків, включно з усіма вкладеними стендами; початкові коди й журнали —
`повна-батарея/`. Після доповнення журналювання іменованими кодами `CHAIN_*` повторено ланцюг (320 перевірок),
самооновлення (22), новий стенд (47), перевірку хешів (10), копії та GPU-моделі — `стенди/`.
У кожного з 27 запусків останній результат — код 0, провалів немає; зведення з посиланнями на журнали —
`результат.json`. Це власні перевірки виконавця.

Початковий повний запуск виявив ще дві передумови стендів. GPU-стенд не ініціалізував `$script:StateDir`,
який за нормального запуску задає Main: додано один рядок ініціалізації у фікстуру (теж у латці), без зміни
перевірок чи виробничих worker/планувальника. Після цього — 110 успішних перевірок, код 0.

Стенд копій на довгому шляху Windows спершу зупинився на `Filename too long`; runner задає `core.longpaths=true`
лише через середовище дочірніх git-процесів. Далі проявилася різниця контрактів: для promisor-клону
Get-ArchiveDirs свідомо повертає порожній список, а стенд перевіряє скорочення повного дерева. Перед повтором
без lazy fetch перевірено всі **32 664 блоби** базового коміту — відсутніх **0**. Лише для процесу цього
стенда задано `remote.origin.promisor=false`; постійний конфіг клону не змінювали. Повтор — 14 успішних
перевірок, код 0 (`повтор-копій/`, включно з `повнота-бази.json`); повна копія 2539,8 МБ скоротилася до
359,5 МБ. Жодної перевірки стенда копій не прибирали й не послаблювали.

Для повтору саме копій: `$env:STATE_DIAGNOSTIC_LOG_SUBDIR='повтор-копій'; python <ця-тека>/прогнати.py
<тимчасове-дерево> сценарії_копії.ps1`. Решту запускає та сама команда без назви стенда.

Незалежної перевірки й встановлення цієї латки не виконували; їх проводить диспетчер. Даних для висновку про
причину історичних інцидентів немає. Вад поза мірилом не встановлено.

## Що встановлено читанням коду

- `queue_lanes.ps1:436–447`, `Get-MarkerState`: перевіряє `.claim`, наявність стану, далі викликає
  `ReadAllText` без локальної обробки помилки читання.
- `wrapper_chain.ps1:390–409`, `Get-ChainMarkerState`: викликає цей читач для `claude-run/state` чи стану
  `gemini-runs`. Його коментар вимагає збереження UNKNOWN для недоступного стану.
- `wrapper_chain.ps1:416–421`, `Get-ChainMarkers`: уже ловить виняток окремої позначки, присвоює UNKNOWN,
  але водночас викликає `Write-ChainFailure`. Отже, сам рядок `CHAIN_FAILED` ще не доводить переривання всього
  проходу на цій голові. Це потрібно звірити зі стеком і версією встановленої копії.
- `gemini_publish.ps1:267–273`, `Get-BadLine`: формує `STATE_INVALID` у шляху читання результату `Get-Line`.
  Спільність фактичної причини з помилкою позначки без журналу не доведена.

Гіпотеза: помилка читання стану однієї позначки проходить до `Write-ChainFailure` через `Get-ChainMarkers`.
Не виміряно фактичний об'єкт, причину недоступності (ACL, тека замість файла, зайнятість чи інше), встановлену
версію обгортки та зв'язок із `STATE_INVALID`. Це не висновок про причину інцидентів.
