# CI-швидше — подача workflow латкою

База наряду: `2e63df53c7df7f1f219dc819fed802f1543eab41`, гілка `gemini/CI-швидше`, ризик Р2, рядки 12258–12259.
У гілці змінено прилад храповика, його стенд і спільний запуск обгортки. Зміни двох workflow — у `workflow.patch`;
файли `.github/` та `аудит/адаптери/gemini/` у гілці не змінені. Латку застосовує диспетчер.

## Захист і перевірка

Храповик подає лічбу голови й бази всіх коренів у спільний `ThreadPoolExecutor`, обмежений `os.cpu_count()`
(якщо ОС не дала числа — один працівник). Спершу підготовлено обидва дерева; тимчасове дерево бази та
відновлені файли голови прибираються після завершення всіх лічб. Результати забираються в початковому порядку коренів. Корені не пропускаються, формат паспортів
не змінено.

`--ознака-стенда` записує `стенд=true/false` у файл виходів CI. Ознака походить із того самого `зачеплені`,
що червонить змішування приладу з кодом: `змінені_файли`, `ХРАПОВИК`, прилади, бази, помічники й рядки паспортів
обох дерев. За невідомої бази ознака консервативно істинна. Workflow спочатку запускає храповик, потім стенд,
якщо ознака не `false`; помилка храповика зберігає червоний результат роботи.
Пошкоджені рядки паспортів порівнюються дослівно: початковий відступ не приховує зміни від стенда.
Допустимі кінцеві пробіли зберігають попередню поведінку класу.

Стенд храповика: ДО 19/19, ПІСЛЯ ті самі 19/19, ще 14 перевірок ознаки та бар'єр одночасності при 1/2/4 ядрах.
Підсумки при цих трьох кількостях працівників однакові. Дві потрібні червоні проби — випадок 1
(`місць 5 → 7`) та випадок 4 (`прилад і виправлення — різними PR`) — червоні і ДО, і ПІСЛЯ:
`храповик-стенд-ДО.log`, `храповик-стенд-ПІСЛЯ.log`. Команда:

```powershell
python -X utf8 джерела/прилади/стенд_храповика_кореня.py
```

Обгортка: 28 стендів, 1280 тверджень, усі підсумкові коди 0. Частини 1/3/4/5 — з першого паралельного прогону,
частина 2 — з повного повтору цієї частини. У першому прогоні нічний стенд упав до тверджень через stderr Git Bash
`could not find /tmp`; його окремий повтор і повтор усієї частини зелені, нічний має 18 тверджень. Причину
разового попередження не доведено. Початковий збій не стерто: `нічний-перший-збій.log`,
`обгортка-перший-прогін.json`. Перший паралельний прогін завершився за 365,750 с, але мав 27/28 зелених стендів;
це не час повного зеленого прогону.

Артефакти успішних частин — `стенди/частина-N.json` і `.log`, час та лічби — `обгортка-локально.json`.
Збирач прочитав рівно 28 результатів, помилок 0. Один перелік `перелік_запусків` визначає виконання та очікуване
покриття. Нічний стенд і хеші входять до нього, парні `.ps1` окремо не дублюються.

`стенд_ci_швидше.py` виконав справжній нічний стенд із підставленим процесом, що друкує `FAIL` та виходить із
кодом 1: збирач червоний. Так само червоні пропуск, дубль, сторонній стенд, нуль тверджень, відсутній код процесу,
порожні артефакти та пошкоджений JSON (`збирач-проби.log`). Команду збирача взято з підготовленого YAML й виконано
через Git Bash: за зелених артефактів `PARTS_RESULT=success` дає 0, `failure/cancelled/skipped` дають 1
(`збирач-статуси.json`). Назва обов'язкової перевірки збережена: `обгортка — Windows PowerShell 5.1`.
Матриця має `fail-fast: false`. Перевірено `git apply --check`, YAML та `actionlint` без помилок.

## Вимір часу й вибір матриці

База саме документного PR: [PR #2737](https://github.com/mightyrochy/kod-shi-data/pull/2737),
[храповик, запуск 41330317661](https://github.com/mightyrochy/kod-shi-data/actions/runs/41330317661/job/124918834658):
15 хв 06 с від початку до кінця роботи, з них стенд 3 с, лічба коренів 14 хв 22 с.
PR змінював лише `аудит/наряди/CI-швидше.md`; метадані — `храповик-CI-ДО.json`.

База PR з обгорткою:
[запуск 41331998639](https://github.com/mightyrochy/kod-shi-data/actions/runs/41331998639/job/124923864494):
26 хв 47 с, із них стенди 25 хв 55 с (`обгортка-PR-CI-ДО.json`, подія `pull_request`).

Для розподілу взято останні два завершені успішні запуски на початок роботи:
[41325719747](https://github.com/mightyrochy/kod-shi-data/actions/runs/41325719747) та
[41323895519](https://github.com/mightyrochy/kod-shi-data/actions/runs/41323895519).
Тривалість кожного стенда — різниця часових позначок рядків `ВИКОНУЄТЬСЯ <назва>` і JSON його результату в
`gh run view <ID> --log`. Повна таблиця 28 стендів — `тривалості.md`, первинні числа — `час-стендів-CI.json`.
Ці два запуски використовуються для ваг матриці; окремий PR вище — для бази порівняння перевірки злиття.

Вага стенда — максимум його двох вимірів. Сума ваг 1831,940 с, найбільша вага 411,230 с
(`сценарії_рушіїв.sh`). Чотири частини за цей час умістили б лише 1644,920 с: їх недостатньо.
Стенди розкладено від найдовшого до найкоротшого в найменш завантажену частину:

| Частина | Стендів | Сума ваг CI, с | Успішні локальні стенди, с |
|---|---:|---:|---:|
| 1 | 1 | 411,230 | 365,657 |
| 2 | 5 | 355,096 | 308,421 |
| 3 | 7 | 355,042 | 344,830 |
| 4 | 7 | 355,435 | 326,359 |
| 5 | 8 | 355,137 | 323,937 |

П'ять частин досягають нижньої межі 411,230 с за цими вагами: більше частин її не зменшить, бо окремий стенд
не ділиться. Кожен стенд рівно в одній частині. Це розрахунок часу стендів, без підготовки машин і збирача.

Локально використано Windows PowerShell 5.1, Git Bash та Python 3.12. CI використовує Python 3.11;
локальний час не видається за вимір CI.

Початкова локальна пара документної проби: ДО 1751,375 с, ПІСЛЯ 287,781 с, обидва коди 1,
підсумки побайтово однакові. Ці цифри **не є часом зеленого CI**: у sparse-checkout не було
`аудит/проби/б1`, а прилад колірних меж отримував `stdout=None` під час читання дочірнього Python.
Усі 15 успішно порахованих коренів мали числа еталонного CI. Помилки й невдалу пару збережено
в `храповик-документ-невдала*`; успішна частина не видається за повний обсяг.

Кодування відтворено окремою пробою (`кодування-локально.json`): ізольований дочірній Python з `-I`
друкує cp1251, батько з UTF-8 отримує помилку декодування в потоці читання та `stdout=None`.
Для фінальної локальної проби розгорнуто `аудит/проби/б1` й узгоджено кодування середовищем
`PYTHONUTF8=0`, `PYTHONIOENCODING=utf-8`: локальний батько правильно читає cp1251 дочірнього процесу,
а зовнішній протокол `місць:` лишається UTF-8. Прилад колірних меж і решту приладів не змінено.

Відтворення повного документного дерева — `вимір_документного_дерева.py`: робоча копія бази з єдиним новим
`аудит/наряди/CI-час.md`, повна потрібна база, всі корені на голові та базі, точні числа з еталонного
[CI коміту 2e63df5](https://github.com/mightyrochy/kod-shi-data/actions/runs/41331898201)
(`еталон-корені-CI.json`). Сценарій вимагає TEMP усередині теки задачі та прибирає власну робочу копію.

**Фінальна локальна проба зелена: 335,672 с (5 хв 35,672 с), код 0, 32 логічні ядра.** Усі 17 коренів
пораховано на голові й базі; кожне число збігається з головою еталонного CI. Для суто документної зміни
файл виходів містить `стенд=false`. Докази — `храповик-документ-ПІСЛЯ.json` і `.log`.
Це повна успішна лічба після підготовки середовища, а не порівняння з невдалою локальною парою.

```powershell
python аудит/латки/CI-швидше/вимір_документного_дерева.py
```

Навіть цей локальний час перевищує 300 с на 35,672 с. Корені не пропущено: у наряді дозволена паралелізація,
а доведених обсягів для їхнього пропуску немає. Гіпотеза залишку — вартість повної лічби приладів;
поосібний час усіх приладів не виміряно, тому конкретний прилад чи підготовку дерев причиною не оголошено.
Фактичні тривалості CI ПІСЛЯ на Ubuntu/Python 3.11 та Windows для обгортки ще потрібні для остаточного висновку.

## Що лишається диспетчерові

Час CI ПІСЛЯ не виміряно: адаптер забороняє цій сесії змінювати `.github/` та пушити;
публікацію гілки й відкриття PR робить обгортка, застосування латки — диспетчер. Тому цілі документний PR ≤5 хв і PR обгортки
≤12 хв поки не підтверджені, рядки дошки 12258–12259 лишаються ЧАСТКОВО. Посилання на майбутні запуски не вигадані.

Застосувати до гілки, яка містить коміти цього наряду:

```powershell
git apply --check аудит/латки/CI-швидше/workflow.patch
git apply аудит/латки/CI-швидше/workflow.patch
```

Після застосування — звичайні PR, що змінюють лише `аудит/наряди/*.md`, і PR обгортки; зафіксувати тривалість
тих самих обов'язкових перевірок та посилання, звірити ознаку стенда і збирач. `workflow_dispatch` не потрібний.
Нічна робота дозволу та хеші обгортки латкою не змінюються. Вад поза мірилом не знайдено.
