## 1. Проблема та інвентар нинішньої взаємодії (ДО)

Система використовує три родини моделей (Claude, OpenAI Codex, Google Gemini), але кожен постачальник інтегрований за окремою спеціальною схемою («костилями»), що створює високу вартість координації, ризики безпеки та постійно вимагає ручного втручання власника:

1. **ChatGPT (Codex):**
   - *Канал:* веб-чат власника з середовищем Codex, коментарі в GitHub issue #963 (три суворі формати: `ПЕРЕВІРЕНО ПАЧКА`, `РІШЕННЯ`, `ПРОБЛЕМА`), черга в #960, ноутбук через коментарі в #996.
   - *Чекання:* сторож звітів — окрема сесія Claude Sonnet medium (`subscribe_pr_activity`), яка кожні кілька ходів «тихо чекає», спалюючи контекст до ~150 тис. токенів.
   - *Проблема:* прив'язка до веб-інтерфейсу власника; ліміт підписки вичерпано 18.10 на 6 діб; не бачить локальних сервісів без коментарів у #996.

2. **Gemini (`agy`):**
   - *Канал:* локальний CLI Antigravity (`agy`) на ноутбуці під окремим користувачем Windows `gemini` (ізоляція ОС налаштована власником 19.10).
   - *Обмін кодом:* через `git bundle` у спільній теці `C:\Users\Public\gemini\`.
   - *Руки власника:* **2 ручні дії на кожен робочий прогін**:
     1. Запуск `agy -p` у сеансі `gemini` з прапорцем `--dangerously-skip-permissions`;
     2. Ручний `git fetch` бандла в чистий клон власника, очна перевірка відсутності змін у `.github/` та ручний `git push`.
   - *Стійкість:* у пробах 13 і 25 агент кидав роботу без звіту й коміту через блокування у фоні (2 з 4 кинуті); argon видає 429 до 25.10; через відсутність прямого пушу робота стоїть на руці власника.

3. **Claude:**
   - *Канал:* сесії платформи, листи-тригери (`create_trigger`, `fire_trigger`), сесія-запускач на мосту ноутбука DESKTOP-6N11SA4.
   - *Запобіжники:* систематичні блокування:
     - `elevated_session_untrusted_device` при спробі підняти міст або виконати команду;
     - `Instruction Poisoning` / `Self-Modification` (≥ 6 випадків за 3,4 доби), коли повноваження наряду чи зняття заборони надходять каналом даних (листом).
   - *Ліміти:* тижневий ліміт вичерпано на 97 % (19.10), через що Claude обмежено лише ролями менеджера, диспетчера та запускача.

## 2. Аналіз варіантів підключення агентів

### Варіант 1: GitHub як єдина шина оркестрації (Issues, Labels, PRs, REST API)

*Опис:* Вся взаємодія переноситься в GitHub. Наряди — це issues з мітками (`наряд:готовий`, `провайдер:gemini`, `провайдер:codex`, `провайдер:claude`). Агент бере issue, створює гілку, робить PR-чернетку. Зміна стану фіксується мітками (`стан:перевірка`, `стан:до-злиття`).
- **Як бере:** опитування REST API (`gh issue list --label "наряд:готовий"`) або webhook.
- **Де й права:** будь-де (хмара або ноутбук).
- **Як віддає:** відкриває PR, звіт у тілі PR.
- **Хто перевіряє:** інший агент призначається рецензентом PR.
- **Хто чекає подію:** polling без моделі (скрипт або GitHub Actions).
- **Руки власника:** 0 (якщо агент має push token) або 1–2 (якщо пуш робить власник).
- **Ціна:** 0 за шину (в межах 5000 req/год з токеном, 60 req/год без входу).
- **Запобіжники:** мінімальні відмови (нема листів-тригерів).
- **Ризики:** у публічному репозиторії сторонні коментарі чи issues можуть спровокувати Prompt Injection. Потрібна сувора фільтрація авторів (`mightyrochy`).

### Варіант 2: Офіційні інтеграції постачальників (Claude Cloud, Codex App, Gemini Code Assist, GitHub Actions)

*Опис:* Використання виключно штатної хмарної інфраструктури розробників: Claude Code Cloud, OpenAI Codex App у GitHub, Gemini Code Assist, GitHub Actions.
- **Як бере:** згадки `@codex`, `@gemini-code-assist` у коментарях PR, workflow_dispatch.
- **Де й права:** хмарні контейнери постачальників.
- **Як віддає:** коментарі до PR або автоматичні коміти в гілку.
- **Хто перевіряє:** боти-рецензенти (Codex, Code Assist).
- **Хто чекає подію:** інфраструктура GitHub.
- **Руки власника:** 0.
- **Ціна:** висока (оплата за токени API, підписки швидко вичерпуються).
- **Запобіжники:** часті блокування Claude при спробі взаємодії з локальними сервісами (`untrusted_device`).
- **Ризики:** 
  1. Gemini Code Assist зараз працює лише як рецензент (не пише великих правок).
  2. Запуск AI-агентів усередині GitHub Actions із правом `contents: write` створює **критичну вразливість**: агент із доступом до коду може змінити файл воркфлоу `.github/workflows/*` і отримати повний доступ до секретів репозиторію. Це прямо заборонено правилом «Безпека» в `AGENTS.md`.

### Варіант 3: Самохостований GitHub Actions Runner під користувачем `gemini`

*Опис:* На ноутбуці встановлюється GitHub Actions Runner, запущений як служба Windows від імені обмеженого користувача `gemini`. Воркфлоу запускають локальний `agy -p` за подіями з GitHub.
- **Як бере:** слухає чергу завдань GitHub Actions (`runs-on: [self-hosted, gemini]`).
- **Де й права:** локальна ізоляція ОС під користувачем `gemini`.
- **Як віддає:** крок воркфлоу пакує результат і робить коміт/PR.
- **Хто чекає подію:** служба Runner (без моделі).
- **Руки власника:** 0 на прогін.
- **Ціна:** 0 додаткових витрат.
- **Запобіжники:** відсутні (runner працює детерміновано).
- **Ризики:** 
  1. У публічному репозиторії self-hosted runner становить загрозу: будь-який зовнішній PR може виконати код на машині, якщо не налаштовано обов'язкове схвалення власника ("Require approval for first-time / all contributors").
  2. Складне налаштування передачі секретів безпечним шляхом.

### Варіант 4: Безголові CLI (`agy -p`, `codex exec`, `claude -p`) під керуванням локального оркестратора без моделі (Рекомендований)

*Опис:* На ноутбуці працює детермінований легкий фоновий процес (PowerShell/Python daemon) без залучення AI-моделі. Він моніторить чергу нарядів (`аудит/наряди/`), запускає агентський CLI у відповідному ізольованому середовищі, контролює час виконання, перевіряє безпеку результату й сам виконує пуш.
- **Як бере:** локальний водій читає наступний наряд із черги за пріоритетом і призначеною силою моделі.
- **Де й права:**
  - Gemini: сеанс користувача `gemini` без прав адміністратора, прапорець `--dangerously-skip-permissions`, робочий клон без збережених GitHub credentials.
  - Claude: `claude -p` у контрольованому середовищі.
  - Codex: `codex exec` у headless-режимі.
- **Як віддає:** агент створює звіт `аудит/<звіт>.md` і локальний коміт.
- **Хто чекає подію:** локальний скрипт-обгортка (таймер/Process.WaitForExit), **0 токенів моделей**.
- **Санітарія та пуш:** обгортка (працюючи поза ізоляцією агента або через контрольований шлюз) перевіряє:
  1. `git diff origin/main --name-only` не містить `.github/`;
  2. Наявний очікуваний файл звіту;
  3. Тільки після валідації обгортка виконує `git push` з обліковими даними водія, створює PR-чернетку й видаляє файл наряду.
- **Руки власника:** **0 рук на робочий прогін**.
- **Ціна:** 0 токенів на очікування й координацію.
- **Запобіжники:** 0 відмов `Instruction Poisoning` (наряд подається прямо на старті в параметрах CLI).

### Варіант 5: Протоколи взаємодії агент↔агент (MCP / A2A)

*Опис:* Агенти взаємодіють через протокол Model Context Protocol (MCP), де спільні інструменти (доступ до файлів, git, запуск тестів, передача завдань) виносяться в стандартизовані MCP-сервери.
- **Як бере/віддає:** виклики JSON-RPC методів MCP.
- **Де й права:** MCP-сервер може реалізувати суворий шлюз безпеки (забороняти читання секретів, забороняти запис у `.github/`).
- **Хто чекає:** залежить від реалізації клієнта.
- **Руки власника:** 0.
- **Ціна:** накладні витрати на контекст JSON-RPC описів інструментів.
- **Оцінка:** MCP — відмінний стандарт для доступу до *інструментів* (наприклад, доступ до LM Studio, ComfyUI, знімків екрана), але сам по собі MCP не є шиною асинхронної черги нарядів і не скасовує потреби в безмодельному водії.

### Як розв'язуються ключові проблеми:
1. **ПК-3 (повноваження листами):** Наряд передається безпосередньо у системний промпт або стартовий аргумент безголового CLI (`-p`). Жодні права, зняття заборон чи інструкції не передаються незахищеними повідомленнями в процесі роботи.
2. **ПК-6 (механіку роблять моделі):** Очікування виконання, відстеження таймаутів, перевірку наявності комітів і санітарний контроль виконує детермінований скрипт водія. Жодна модель не сидить у `sleep`-циклах і не спалює дорогий контекст.
3. **Руки власника:** Зменшуються з 2 до 0. Власник один раз налаштував користувача `gemini` — далі запуск, перевірку та пуш повністю бере на себе водій.
4. **Безпека:** Ізольований агент не має доступу до ключів GitHub (push token / SSH key). Пуш виконує виключно водій після автоматичної перевірки відсутності правок у `.github/`.

## 5. Доля нарядів М.1 і М.2

- **Наряд М.1 («Чекання без моделі»):**
  - *Вердикт:* **ЗМІНИТИ ТА ОБ'ЄДНАТИ.**
  - *Обґрунтування:* М.1 планувався як заміна сесій-сторожів Claude для відстеження CI голови PR. Замість окремого хмарного сторожа, функція очікування CI стає частиною детермінованого циклу:
    - Диспетчер під час свого щогодинного пульсу перевіряє статус PR через GitHub REST API або `gh pr checks` (0 викликів сторонніх моделей);
    - Або локальний водій самостійно чекає завершення CI перед передачею пачки на перевірку.
  - Потреба в окремих сесіях-сторожах відпадає повністю.

- **Наряд М.2 («Gemini без руки власника»):**
  - *Вердикт:* **ЛИШИТИ ЯК ПЕРШИЙ КРОК ВПРОВАДЖЕННЯ (із уточненням).**
  - *Обґрунтування:* Оскільки ізоляцію ОС власник уже успішно налаштував 19.10 (користувач Windows `gemini`, `agy` під ним), наряд М.2 має сфокусуватися на створенні скрипта-водія (`джерела/прилади/водій_gemini.ps1`), який:
    1. Запускає `agy -p` з правами користувача `gemini`;
    2. Забезпечує догонку при виході без звіту (як у `блок_власника.ps1`);
    3. Автоматично перевіряє дифф на відсутність `.github/`;
    4. Автоматично пушить готову гілку з клону власника.
  - Це ліквідує 2 ручні дії власника вже зараз.

## 6. Пропозиції змін до чинних правил на рішення власника

1. **Дозвіл локальному водієві на автоматичний push гілок `gemini/*` та `codex/*`:**
   - *Поточне правило (`AGENTS.md`, «Нікому»):* заборона неконтрольованого пушу, пуш робить власник зі свого сеансу після перевірки.
   - *Пропозиція:* дозволити скрипту-водію на ноутбуці автоматично пушити гілки `gemini/*` та `codex/*` за обов'язкової умови проходження локального автоматичного гейту:
     `git diff --name-only origin/main` не містить файлів з префіксом `.github/`.
