## 1. Рішення, яке рекомендовано

**Рекомендовано спільну хмарну роботу через GitHub: Codex cloud і Claude Code cloud виконують кодові наряди; стандартний Gemini app бере дослідження й незалежний аналіз, а його Tasks варто випробувати на окремій хмарній задачі.** Ноутбук — лише для GPU та локальних сервісів. За уточненнями власника Jules недоступний, а для Gemini він насамперед розглядає звичайний застосунок. Автоматичне повернення GitHub-правок із Gemini app ще не підтверджено; CLI, VM і нові ресурси не обрані.

Спочатку зіставити можливості й квоти трьох конкретних підписок, використати готові хмарні механізми й довести доступні маршрути «наряд → результат → незалежна перевірка». Невеликий безмодельний шлюз закриває лише підтримувані передачі, контроль дублів і станів; він не створює неіснуючого API звичайного чату. Злиття лишається чинному диспетчеру з повним SHA та зеленим CI; менеджер лишається Claude за чинним правилом.

**Нове уточнення змінює порядок: спершу корисні ролі й хмарний пілот трьох підписок, потім М.1 та подальша автоматизація за потреби.** М.2 замінити як спосіб: його ціль зберегти, але вибір автономного Google-виконавця робити лише після пілота застосунку. Попередню пропозицію підписного Gemini CLI OAuth відкликано через офіційну депрекацію (§4а). Повний контролер за 15–24 людино-дні — умовне пізніше розширення, не початкова вимога. Підписка не дорівнює API-кредитам або безкоштовному хостингу.

Числа не виправдовують велику платформу лише економією грошей. Усі історичні сторожі разом мають $37,86 записаних витрат за 3,427 доби; це не $38 самих холодних стартів і не рахунок за підписку. Головна користь — менше ручного Gemini, втрачених переходів, повторного контексту й залежності від ліміту Claude. У новій вибірці 16 пачок фінальний звіт тієї самої SHA доходив до merge за медіанні 2 хв 08 с; довший час був до фінальної готовності. Тому спершу виправляємо стан, права й виконання, а не останню хвилину злиття. [Відтворений облік][CSV], [історичний аналіз][А31]; повна нова таблиця — додаток Б.

Чернетка Gemini правильно пропонує винести механіку з моделей, але її гарантії «повна ізоляція», «0 відмов», «0 кинутих», «0 вартості» не доведені. Стартовий `-p` не є системним дозволом; Windows-користувач не є доказом повної ізоляції; заборона `.github/` не закриває непрямий запуск змінених скриптів у привілейованому CI. Повний реєстр усіх її кількісних тверджень — додаток А.

## 4а. Конкретна хмарна робота та вибір Google-маршруту

Це доповнення за новою постановкою власника: організувати спільну роботу з початку, у хмарі й на ноутбуці, а не лише оптимізувати локальні обгортки. Jules виключено за повідомленням власника; обхід недоступності не пропонується. **20.10 власник підтвердив Google AI Pro.** CLI/VM та нові ресурси він не обрав.

| Маршрут | Де виконується | Як під'єднати до роботи Люстерка |
|---|---|---|
| **ChatGPT → Codex cloud** | Штатне хмарне середовище Codex, підключене до GitHub | Наряд із посиланням на прийняту ревізію, своя `codex/…` гілка й PR. Конкретний автоматичний trigger/повернення результату перевірити на одному наряді; `@codex review` сам не є універсальним запуском виконавця |
| **Claude → Claude Code cloud** | Штатна хмарна сесія; за доступності — routines | Виконання або незалежна QA, `claude/…` гілка/звіт у PR. Використати підтримуваний cloud-запуск/подію; врахувати caps і явний результат, а не тільки зелений run |
| **Google → стандартний Gemini app** | Штатний застосунок; за доступності тарифу — хмарні Tasks | Дослідження, варіанти рішення й незалежний аналіз за точними матеріалами. GitHub-import є знімком коду без історії/PR-метаданих і права запису; не видавати це за автоматичного PR-виконавця |

**Звичайний Gemini app придатний для частини спільної роботи.** Офіційний GitHub-import читає знімок до 5 000 файлів/100 MB; він не включає commit history, PR metadata або запис у репозиторій. Для незалежного висновку треба зафіксувати, який код/діфф і докази він бачив; висновок за довільним знімком не є QA поточної голови PR. [Імпорт GitHub](https://support.google.com/gemini/answer/16176929).

**Tasks у Gemini app — реальне хмарне виконання**, з браузером і кодом, яке може тривати без ноутбука; документація називає AI Pro/Ultra. Тому обмежувати застосунок лише відповідями чату теж неправильно. Але повний цикл GitHub-наряд→гілка→PR, доступний програмний запуск і entitlement власника не перевірені. Custom MCP наразі обмежений США та передбачає ручне підтвердження записів — це не готовий автоматичний міст для власника в Україні. [Tasks](https://support.google.com/gemini/answer/17094507), [custom MCP](https://support.google.com/gemini/answer/17209137).

**Ліміти треба дивитися окремо в app і фактичному `agy`.** Для Google AI Pro app описує 4× стандартний compute-ліміт із п'ятигодинним і тижневим вікнами; актуальне використання видно в **Settings → Usage Limits**. Це не фіксована кількість повідомлень: витрата залежить від роботи моделі й інструментів. Старі CLI-цифри requests/day не переводяться в повідомлення або Tasks. [Ліміти Gemini app](https://support.google.com/gemini/answer/16275805).

Antigravity Pro окремо описує підвищені модельні квоти з п'ятигодинним відновленням до тижневої межі; для встановленого `agy` дивитися **`/usage` або `/quota`** й конкретну модель. Документація не підтверджує тут ні спільний, ні повністю незалежний app↔agy quota pool. Однакові часові вікна не доводять один кошик. Це різні інтерфейси й одиниці використання, тому загальний «відсоток Gemini» не виводимо. [Antigravity plans](https://www.antigravity.google/docs/plans), [CLI usage](https://www.antigravity.google/docs/cli/commands/usage/).

**Попередній підписний Gemini CLI fallback відкликано.** Офіційне повідомлення, оновлене 09.10.2026, каже про припинення consumer Login with Google у Gemini CLI з 18.06, включно з AI Pro/Ultra; сторінки geminicli.com із описом такого входу суперечать цій новішій депрекації. Cached auth не є підставою будувати нову систему на непідтвердженому доступі. Якщо після пілота app потрібний автономний Google-кодовий вузол, окремо дослідити дозволений direct scripting/CI офіційного Antigravity `agy`, а не використовувати consumer-вхід як backend стороннього агента. Хост і credentials тоді окремо погоджуються. [Депрекація](https://developers.google.com/gemini-code-assist/docs/deprecations/code-assist-individuals), [Antigravity FAQ](https://www.antigravity.google/docs/faq).

**Один наскрізний крок:** Gemini app за потреби досліджує конкретне питання → менеджер ставить погоджений наряд у GitHub issue → Codex або Claude робить гілку/PR → інший агент перевіряє поточну SHA → потрібний CI → диспетчер зливає → підсумок менеджеру. Виконавець/перевірка обираються за силою й задачею, не за обов'язковим проходженням усіх трьох брендів. Якщо повернення висновку Gemini потребує перенесення людиною, це видимий компроміс, а не заявлена автономність.

Наявні файли нарядів лишаються джерелом змісту; один issue і його PR тримають результат і питання, не створюючи другої дошки симптомів. Короткий спільний контракт: task/revision, база, мета, межа, сила, приймання; результат: run, PR/SHA, докази, готово/частково/блокер.

Для початку достатньо одного видавця призначень та запису `task/revision/run`, відповідального агента, ID події/запуску й точного SHA. Повторна подія не створює другого запуску; невідому долю старого запуску звіряють перед переназначенням. Мітка GitHub показує стан, але не є атомарним claim. Стартовий наряд не підвищує права; нова голова знімає допуск старої QA.

**Native hooks — перший вибір, малий шлюз — лише для підтримуваних прогалин.** Для Codex/Claude використовуються підтверджені механізми їхніх cloud-продуктів. Для app Gemini повна автоматична передача ще не доведена; шлюз не створює неіснуючого API чату. Публічний Actions-job із перенесеним ChatGPT `auth.json` не є скороченням шляху. [Codex CI/CD](https://learn.chatgpt.com/docs/non-interactive-mode), [Claude cloud](https://code.claude.com/docs/en/claude-code-on-the-web), [routines](https://code.claude.com/docs/en/routines).

Власник щодня задає мету в одному менеджерському чаті й отримує зведення: завершено, працює, потрібне рішення. Одноразове під'єднання GitHub, OAuth-вхід і повторна авторизація — окремі інфраструктурні дії, не приховані під «0 рук». Код, документація й хмарна QA працюють із вимкненим ноутбуком; локальний піднаряд потрібний лише для GPU/LM Studio/ComfyUI чи іншої справді локальної можливості.

Виконавці й перевірки розподіляються за достатньою силою та квотами. **Чинне правило про Claude-менеджера зберігається.** Передача менеджерської ролі іншому постачальнику — окрема пропозиція у §9, не вже здійснена заміна при ліміті.

## 5. Порівняння п'яти варіантів

Ціна — відносна інженерна оцінка для цього проєкту; точні гроші без тарифів і часу людей не виводяться. «0 рук» — можлива штатна мета після налаштування, не відсутність повторного входу, квот або рішень власника.

| Варіант | Як бере / віддає / чекає | Руки й ціна | Відмови та безпека | Висновок |
|---|---|---|---|---|
| **1. GitHub як шина** | Наряд/issue → PR/звіт; webhook/poll без моделі | Руки залежать від запуску й push. Мале–середнє налаштування; REST не є всією ціною | Labels/comments не блокують гонки; текст від знайомого login не є authority. CI/ключі треба розділити | Використати як людський журнал, не як єдиний state machine |
| **2. Офіційні інтеграції, cloud, routines, Actions** | Підтримуваний trigger → cloud task/review/артефакт; чекає сервіс | Мале налаштування окремого доступного сценарію; середня складність повного узгодження. Підписки/API залежать від продукту | Квоти, caps, неоднакові права/моделі; огляд не замінює QA пачки; policy-відмови лишаються | **Основа початкового Codex/Claude-маршруту**, разом із GitHub; можливості перевіряються до власного scheduler |
| **3. Self-hosted runner для локального `agy`** | GitHub job → CLI під окремим користувачем → артефакт/шлюз; це не deprecated consumer `gemini` CLI | Ціль 0 рук; велике налаштування ізоляції, машина/електрика/догляд | Постійний runner у public repo на особистому ноутбуці — високий ризик. Approval PR не очищає хост. CLI keyring/права service-session не доведені | Не перший крок; за потреби лише відокремлений відновлюваний вузол |
| **4. Мінімальний шлюз / повний контролер** | Зафіксований наряд → підтримуваний worker → PR/артефакт → незалежний QA | Спершу лише підтверджені відсутні передачі; повний контролер або власний host — окрема ціна й рішення | Потрібні контроль дублів, ревізій і credentials; шлюз не усуває відсутність API app | **Доповнення до 1+2**, не передумова всіх cloud-запусків; Google-вузол лише після вибору підтримуваного продукту |
| **5. MCP/A2A як основа** | Протокольні tools/tasks/artifacts; runtime треба додати | Руки залежать від реалізації; велика початкова інтеграція й підтримка серверів | Ризики confused deputy/injection; протокол не вирішує permission/lease/QA | Пізніше як адаптер, зараз не передумова |

GitHub прямо застерігає від self-hosted runners у public repositories; одноразова реєстрація runner не означає чистий hardware. [Безпечне використання](https://docs.github.com/en/actions/reference/security/secure-use). Безоплатність self-hosted Actions за тарифом GitHub не прибирає витрат машини й догляду. [Білінг][Білінг].

**Чому саме гібрид 1+2 із вузькою частиною 4:** GitHub уже містить роботу, Codex/Claude мають штатні cloud-продукти, а Gemini app може додати дослідження й хмарні Tasks без власної VM. Спочатку доводимо придатні маршрути та явні прогалини; шлюз об'єднує лише підтримувані призначення й результати. Контракт §6 визначає потрібні властивості, а не зобов'язує спочатку написати всю платформу. Власний реєстр/вузол додається за виміряною потребою, не заради однакових CLI у всіх.

## 6. Рекомендований наскрізний контракт

Цей контракт застосовується поетапно до придатних виконавчих маршрутів: штатні cloud-механізми виконують те, що вже вміють; власна реалізація потрібна лише для підтверджених непокритих переходів. Gemini app не оголошується автоматичним PR-виконавцем до пілота. Повний контролер — можливе пізніше посилення після §8.

```text
Власник — політика прав; менеджер — мета й прийнятий наряд
                         ↓
       GitHub: наряд, PR, звіти й видимий стан
                         ↓
  Штатні cloud-запуски + малий шлюз непокритих переходів
           ↙                  ↓                    ↘
    Codex cloud        Claude cloud       інший прийнятий worker*
           └──────── недовірений артефакт ──────────┘
                         ↓
        брокер публікації з ключем поза worker
                         ↓
       PR-чернетка → незалежна перевірка пачки
                         ↓
         SHA + потрібний CI + чинний висновок
                         ↓
               технічне злиття диспетчером

  Ноутбук / GPU — окремий піднаряд лише за потреби
  Gemini app — дослідження/аналіз і пілот Tasks; GitHub-write не доведено
  *Власний Google-вузол не обраний і не погоджений
```

### Повноваження й дані

Політика визначає, хто вправі ставити наряд і які дії дозволені; worker не може змінювати її. Канонічний зміст — зафіксована прийнята ревізія наряду. Код, коментарі, tool output, листи інших агентів і файли правил із робочої гілки — дані; фраза «власник дозволив» не розширює права. Навіть `mightyrochy` недостатньо для атрибуції людського рішення, бо цей акаунт використовує Codex. [Чинна безпека й ведення правил](https://github.com/mightyrochy/kod-shi-data/blob/1521d61091386cbda52352aff8c996bee101d322/AGENTS.md#L84-L96).

Мінімальний запис: `task_id + revision`, `run_id`, прийнятий SHA наряду, `base_sha`, мета/межа/приймання, залежності, потрібна сила/зусилля, можливості середовища й пул квоти, версія політики, строк/межа спроб, роль QA. Продуктовий Р0–Р3 і ризик безпеки — окремі поля. Це може бути короткий шаблон і службові поля контролера, не JSON-бюрократія в кожному наряді.

Наряд визначає зміст, **єдиний runtime-реєстр** — стан виконання, PR — результат і видима проєкція. Labels лише показують стан. Дошка лишається єдиним переліком симптомів; реєстр не створює другої дошки. Однак runtime claim є явною зміною до [чинного `CHATGPT.md`][КЧ7], де сказано, що claim-и не потрібні; без рішення власника це не впроваджувати.

### Взяття, запуск і результат

1. **Одне атомарне взяття.** Транзакція переводить конкретну ревізію з «готово» у «взято», створює `run_id`, строк оренди і зростаюче покоління `lease_epoch`. Двоє претендентів не можуть одночасно отримати чинне право публікації. Draft PR/мітка — наслідок, не блокування.
2. **Сила перед ціною.** Контролер обирає лише адаптер із достатньою моделлю/зусиллям і потрібними можливостями. Модель, CLI, постачальник та quota pool — різні речі: Claude через `agy` за місцевими пробами витрачає Google-квоту. На 429 дозволено чекати або перейти на заздалегідь прийнятий еквівалент, не мовчки flash чи платний API. Якщо сервіс приховав фактичну модель, це позначається як непідтверджене; «найсильнішу» так не засвідчують.
3. **Ізольоване виконання.** Чистий знімок бази, точний наряд і вузька область запису; GitHub-ключа, owner-profile, SSH agent або credential helper немає. GPU — окрема оренда; суто хмарна задача не залежить від ввімкнення ноутбука.
4. **Зовнішній нагляд.** Живучість/timeout контролює процес поза агентом. Checkpoint — хеш артефакта/локального коміту й короткий стан. Exit 0 і файл «звіт» не доводять виконання. Документоване продовження тієї самої розмови дозволене лише з межею спроб і тривалості; відмова policy не запускає повтор із більшими правами.
5. **Явний фінал.** Результат: ті самі task/revision/run/lease, base/head SHA або хеш дерева, фактичні модель/зусилля й версія адаптера, зміни, докази ДО/ПІСЛЯ, статус «готово/частково/заблоковано». Старий lease після відновлення може повернути цінний артефакт, але не має права переписати нову гілку.

### Публікація без передачі ключа агенту

Брокер — маленький довірений процес, окремий від worker. Він приймає недовірені байти у карантин, перевіряє manifest/хеш/область, а Git-операції робить довіреним binary у власному чистому сховищі з контрольованим середовищем і remote. Не запускає тести, hooks, скрипти чи пакетні менеджери агентського checkout. Шляхи/гілки не вставляються рядком у shell.

Цільова гілка визначається контролером; лише дозволений repo/prefix, ніякого `main` чи стороннього URL. Повтор запиту з тим самим ключем ідемпотентності повертає вже створений PR/ref. Зміна ref порівнює очікувану стару голову. Публікуються рівно ті заморожені байти, які перевірено; якщо брокер перебудував коміт, новий SHA стає канонічним **до** QA.

Ключ GitHub має мінімальні потрібні права, merge спочатку відокремлений. Credential не повинен дозволяти worker зробити публікацію в обхід broker. Нових секретів дослідження не створює: спосіб виділеного доступу — рішення власника, якщо наявний дозволений шлях не підходить.

### Незалежна перевірка й актуальність SHA

Перевірка — інша сесія/`run_id`, окремий контекст, бажано інша родина за чинною програмою. Її сила визначена кроком, а не найдешевшою вільною квотою. Виконавець не редагує чужі докази й не позначає себе незалежно перевіреним. PR-боти — додаткові рецензенти, не заміна приймання пачки.

Пачка фіксує список `(PR, head_sha)`, базу, голову/дерево, конфліктні зміни й підтвердження включення складників. Наявність доданого рядка в дереві — сигнал втрат, не доказ збереження поведінки. Глибина лишається за Р0–Р3; очі й живі прогони не підміняються лічбою CI. Живий ПІСЛЯ Р3 може йти після merge за чинним правилом, але має збережене зобов'язання, відповідальну роль і строк.

Допуск до merge зв'язує повний SHA голови, базу/інтегроване дерево, склад пачки, потрібні checks/run IDs із відомим джерелом, версію наряду й незалежний висновок. GitHub може тестувати синтетичний merge-SHA; його треба відрізняти від PR head і пов'язати з конкретною парою head/base. `pending`, `cancelled`, відсутній check чи старий зелений run не є готовністю.

Наряд закривається після злиття потрібного результату, а не після exit 0, появи звіту чи видалення файла наряду у feature-гілці. Залежні кроки розблоковуються за фактом прийнятого злиття; складники пачки закриваються після підтвердження включення. Післязлиттєвий CI main і живий ПІСЛЯ мають власні збережені очікування.

**Новий push інвалідовує допуск старої голови.** Пізній «ПЕРЕВІРЕНО H1» після появи H2 лишається історією H1. Перед merge — свіже читання PR/CI й атомарне `expectedHeadSha` разом із захистом гілки. Рух main може змінити інтеграцію; повторно потрібні перевірка нового дерева й CI. Доведене суто технічне оновлення дозволяє перевикористати очні/живі докази в їхній незміненій області. Новий код/конфлікт/недоведена еквівалентність — перевірка зміненої частини. Це уточнення чинного «перевірене вдруге не перевіряють», а не вимога повторити всю батарею без причини.

### Події й recovery без моделі

Webhook або таймер будить програму; вона читає актуальний стан джерела. Подія — сигнал перевірити, не наказ. Журнал зберігає cursor, ID події й факт обробки; зміна стану та намір повідомлення записуються однією транзакцією (outbox). Повтори з обмеженням і наростаючими паузами, дедуп та періодична звірка відкритих очікувань закривають пропущений webhook, edit і перезапуск.

Семантика — доставка щонайменше один раз плюс ідемпотентне приймання, не недоведена «рівно один раз». Лише нова робота, яка потребує судження, запускає модель. Якщо конкретна хмарна платформа не має дозволеного wake-up API, контролер зберігає готовність і використовує підтримуваний канал; не обіцяє автоматичне пробудження неіснуючим засобом.

| Збій | Дія | Захищена властивість |
|---|---|---|
| Worker зник, повернувся після нового запуску | Прострочити стару оренду, перевірити долю процесу, видати нове покоління; старий результат — в історію | Один чинний видавець; дубль обчислення можливий під час network partition, дубль публікації відсікається |
| Контролер упав після push до запису успіху | Звірити remote ref/SHA/PR та дописати успіх ідемпотентно | Без другого PR/повторної дії |
| Подію загублено/подвоєно | Reconciliation/дедуп, поточний стан сильніший за порядок листів | Відновлення після простою |
| Ноутбук вимкнено/офлайн | Локальні задачі чекають; cloud/CI живуть окремо; локальний результат зберігається | Ввімкнення людиною не маскується як «0 рук» |
| Квота, 429, auth | Обмежені повтори/охолодження; дозволений еквівалент або `blocked_quota/auth` | Без мовчазного зниження сили чи нового API |
| Policy/classifier refusal | Точна причина й заблокована дія, одна адресна ескалація | Не обходити іншою моделлю, каналом чи підвищенням прав |
| Нема незалежної сили QA | Збережене «чекає перевірки», інша доступна робота | Квота не знімає незалежність |

Контролер бажано розмістити на вже дозволеному постійному вузлі поза ноутбуком. Якщо такого нема, локальний пілот допустимий, але час вимкнення — недоступність сервісу; цілодобову надійність не обіцяти. Новий хостинг/credential — окремі витрати й рішення. Моделі потрібні тільки для змісту, а не для «пульсу, що перевіряє, чи працює пульс».

## 7. Межі безпеки, які не закриває `.github/`

**Є конкретний непрямий шлях у цьому репозиторії.** Job `zbirka` оголошує `contents: write`, робить checkout і запускає `джерела/звірка_вантажу.py`; цей Python-крок не обмежений лише main, на відміну від наступного кроку коміту. Зміна цього файла змінює виконуваний код, не торкаючись `.github/`. Ефективні права залежать також від події й налаштувань GitHub; експлуатацію не проводили. [Зафіксований workflow, рядки 513–547](https://github.com/mightyrochy/kod-shi-data/blob/1521d61091386cbda52352aff8c996bee101d322/.github/workflows/zbirka.yml#L513-L547).

Тому потрібні такі межі нового водія:

- PR-код виконується без write-ключа й секретів. Привілейований publisher використовує довірений код із прийнятої ревізії та перевірені артефакти; не checkout довільної PR-гілки з наступним запуском її скрипта.
- `.github/` лишається забороненим для звичайних задач, але окремо враховуються build/test scripts, імпорти, package hooks, local actions, залежності, конфіги й дані, які стають командою. Неможливо вирішити це забороною всього Python/JS — головна межа саме відсутність привілеїв при виконанні.
- Не копіювати агентський `.git`; не довіряти Git config, hooks, `core.sshCommand`, helpers, alternates, `PATH`, shell startup. Не запускати код із shared folder під власником.
- Імпорт перевіряє реальні шляхи й типи: symlink, submodule, Windows junction/reparse, `..`, абсолютні шляхи, регістр/нормалізацію. Звичайний `diff --name-only` цього не гарантує.
- Worker не може змінити broker/policy/log; перевірка й push стосуються того самого immutable artifact.

Не змішувати різні GitHub permissions: `contents: write` не дає автоматично всі secrets чи право редагувати workflow для будь-якого credential. Workflows scope, PAT/App/GITHUB_TOKEN, job env та event відрізняються. Так само події від `GITHUB_TOKEN` мають спеціальну поведінку: поточні docs для PR відкриття/оновлення описують runs із required approval, тоді як більшість інших породжених подій не запускає наступний workflow. Автопуш не гарантує безручний CI без проби конкретного credential/trigger; `workflow_dispatch` зараз заборонено. [Contents permissions](https://docs.github.com/en/rest/repos/contents#create-or-update-file-contents), [GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token), [ризики workflow_run](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run).

Окремий Windows-користувач корисний, але `whoami`, відмова `net session` і відсутність KEY у env не перевіряють ACL дисків/Public, owner-profile, Git Credential Manager, SSH-agent, IPC, служби й мережу. WSL2 також має автомонтування, interop і спільні теки: його назва не є доказом ізоляції. Відновлювана VM/окремий вузол без owner mounts — зрозуміліша межа для недовіреного коду; придатність для GPU/LM Studio треба виміряти, а не припускати.

GitHub/merge/owner credentials обов'язково поза worker. **Inference auth — окрема проблема:** якщо CLI зберігає OAuth у профілі, доступному його tool-shell, агент фактично може його читати. Потрібний підтримуваний поділ клієнта й інструментів або чесно прийнятий залишковий ризик обмеженого входу; не писати «жодних ключів в агента». LM Studio/ComfyUI давати лише потрібні endpoints, без широкої локальної мережі й адміністративного доступу.

Це приймання нового сервісу з ключем, не новий аудит продукту «на кожну помилку». Ніякі прапорці небезпечного режиму не скасовують чинної заборони обходу запобіжника.

## 8. М.1, М.2 і поетапний план

**М.1 — ЗМІНИТИ, виконувати після початкового хмарного пілота.** Зберегти мету й чинний Р1: довговічне безмодельне чекання потрібних подій, SHA, дедуп/recovery й підтримувана доставка. Пілот покаже, які очікування вже закриває native cloud. Для решти — shadow-режим; прибирати лише замінені сторожі, не переносити polling у диспетчерський пульс.

**М.2 — ЗАМІНИТИ спосіб, зберегти ціль.** Спершу встановити корисну роль стандартного Gemini app і межі його Tasks, як просить власник. Якщо потрібне автономне Google-виконання коду понад ці можливості, менеджер ставить окремий наряд на підтримуваний продукт і безпечну публікацію; не починати автоматично з ноутбука або VM. Чинний локальний `agy` можна зберігати як наявну можливість, але не видавати його квоту за app-квоту. **Чинний М.2 має Р3**: звіт його не знижує; нові підкроки та ризик credentials визначаються окремо. [М.1][М1], [М.2][М2].

Оцінка нижче — людино-дні з реалізацією й незалежною перевіркою, приблизно 6–8 год зосередженої роботи на день; не календарний строк і не токени. Очікування квот/власника/пілота окремо. Моделі — сила з чинного словника, реальний ID/доступність підтверджує адаптер; сильніша доступна модель дозволена, слабша без рішення — ні.

Попередні **15–24 людино-дні** залишаються лише грубим орієнтиром повного власного контролера з усіма адаптерами; після пілота обсяг треба перерахувати, повторно не оплачуючи вже доведені механізми. Нові VM, credentials і хостинг не погоджені; їхня вартість та адміністрування окремі. Вигоду не обчислювати множенням 59% на всі історичні витрати.

Мінімальні сценарії приймання самого нового водія: два claims; duplicate/missed webhook; reboot між push і записом успіху; пізній старий lease; нова голова перед merge; старий зелений CI; ноутбук офлайн; 429; soft-denial/exit 0; policy refusal; symlink/Git-config у вантажі; змінений непрямий CI-скрипт без `.github/`. Вони не додаються як постійна продуктова батарея.

## 9. Окремі пропозиції правил власникові

Жодну не застосовано. Вартість рішень А–Ж включена у відповідні кроки плану й не додається вдруге; необов'язкове рішення З має окрему оцінку. Заборони `main`, `workflow_dispatch`, auto-merge, платних API й нових секретів чинні.

|---|---|---|---|
| **А. Єдина хмарна черга й мінімальний runtime-стан** | Issue посилається на прийнятий наряд; PR — результат. Виняток із «claim-и не потрібні» лише для потрібного task/revision/run/lease; дошка лишається переліком симптомів | Кроки 0,4; Р0 правил / високий | Один видавець призначень; не нова паралельна дошка |

## Додаток В. Коротке відтворення

Команди лише читають Git/REST. Локальний checkout може бути новішим: CSV явно читається через `git show` за дослідницьким SHA, який має бути у клоні. Неавторизоване читання public REST можливе з окремим лімітом IP.

### В.2. Звіти #963 і PR

```python
# read-only: лише gh api GET. Дані API змінні; межі created_at зафіксовані.
import subprocess, json, re, datetime, statistics

def get(path):
    s = subprocess.check_output(['gh', 'api', '--paginate', path], text=True).strip()
    pages = []
    while s:
        value, used = json.JSONDecoder().raw_decode(s)
        pages.append(value)
        s = s[used:].strip()
    return [x for page in pages for x in page] if isinstance(pages[0], list) else pages[0]

repo = 'repos/mightyrochy/kod-shi-data/'
start, end = '2026-10-15T00:00:00Z', '2026-10-19T00:00:00Z'
reports = {}
for c in get(repo + 'issues/963/comments?per_page=100'):
    if not start <= c['created_at'] < end:
        continue
    m = re.match(r'ДЛЯ CLAUDE:\s*ПЕРЕВІРЕНО ПАЧКА\s*#(\d+)\s+([a-f0-9]{40})', c['body'])
    if m:
        reports.setdefault(m[1], []).append((c['created_at'], m[2], c['id']))

dt = lambda s: datetime.datetime.fromisoformat(s.replace('Z', '+00:00'))
seconds = []
for number, rs in sorted(reports.items(), key=lambda x: int(x[0])):
    pr = get(repo + 'pulls/' + number)
    latest = max(rs)
    if not pr['merged_at'] or latest[1] != pr['head']['sha']:
        print('виключено', number, pr['state'], pr['merged_at'])
        continue
    lag = (dt(pr['merged_at']) - dt(latest[0])).total_seconds()
    seconds.append(lag)
    print(number, pr['created_at'], latest, pr['merged_at'], lag)
print('N, median/min/max', len(seconds), statistics.median(seconds), min(seconds), max(seconds))
```
